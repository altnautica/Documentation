Mission Control runs fully without a backend. USB, Bluetooth and LAN connections, every configuration panel, mission planning and LAN video work offline. Signing in to a Convex backend adds the features below. The hosted version at [command.altnautica.com](https://command.altnautica.com) has a backend; a build from source needs `NEXT_PUBLIC_CONVEX_URL` (see [Install Mission Control](/mission-control/installation#environment-variables)).

## What signing in adds

| Feature | Signed out (Local only) | Signed in |
|---|---|---|
| USB, Bluetooth and LAN connections | Yes | Yes |
| Configuration panels and mission planning | Yes | Yes |
| LAN video | Yes | Yes |
| Missions and preferences | This browser only | Synced across devices |
| Paired drones listed on every device | No | Yes |
| Cloud relay to drones on other networks | No | Yes |
| Pairing with a generated code | No | Yes |
| Flight log sync | No | Yes |
| MCP remote reach | No | Yes |
| Extension install records and jobs | Read from the agent on the LAN | Also stored in the cloud |

Until you sign in, the top bar shows **Local only** and a banner notes that your data is saved in this browser only.

## Sign in and roles

Mission Control uses Convex Auth with email and password. Click **Local only** in the top bar to open the sign-in dialog. In a build with no backend the dialog reads **Cloud Not Available**; choose **Continue in local mode**.

Each account has a profile with one of these roles:

| Role | Meaning |
|---|---|
| `pending` | The default for every new profile. Waits for an admin. |
| `pilot` | An approved operator account. |
| `alpha_tester` | An approved tester account. |
| `admin` | Manages users and roles. |
| `rejected` | Denied access. |

No one becomes admin automatically. On a backend you run, set one of these before the first sign-in:

```bash
npx convex env set ADOS_BOOTSTRAP_ADMIN_EMAILS you@example.com
```

When the first profile is created and its email is on that list, it becomes admin. If the list is empty, `ADOS_ALLOW_FIRST_USER_ADMIN=1` makes the first profile admin instead. After that, admins change roles for everyone else.

## Cloud relay

The cloud relay reaches a drone that is not on your network, for example one on a cellular uplink. It is the secondary path: on the same network, pair the agent by hostname or IP and Mission Control talks to it directly with no account (see [Connect to a drone](/mission-control/connecting#through-the-ados-agent)).

The relay has three layers:

- **Convex**: the agent posts status to the backend and polls a command queue. Mission Control subscribes to reactive queries. This needs nothing beyond the backend.
- **MQTT**: live telemetry and status over an MQTT broker with WebSocket transport.
- **WebRTC**: video peer to peer, with the offer and answer relayed through MQTT (the **P2P MQTT** transport on [Video feed](/mission-control/video-feed)).

Mission Control switches to cloud mode when it is served over HTTPS. Topic names and the message layout are on [Cloud infrastructure](/architecture/cloud-infrastructure). The agent side is on [Cloud relay](/drone-agent/cloud-relay).

The self-hosted stack also includes a video relay that converts RTSP to WebSocket fMP4. Mission Control's transport switcher does not use it.

## Flight log sync

When signed in, flight records from the Logs tab sync to your account, so they appear on every device. See [Flight logs](/mission-control/flight-logs).

## MCP remote reach

Signed in, you can mint MCP credentials on the [MCP tab](/mission-control/mcp). A credential lets an AI client reach your fleet through the cloud relay when you are off the drone's network, with scopes and an audit trail.

## Community

**Community** in the top bar opens `/community`: the **Changelog** of releases, with reactions, and a **Contact** form. The changelog also drives the "What's New" notification; turn it off under [Settings → Notifications](/mission-control/settings#notifications).

## Backend data

The `convex/` directory in the Mission Control repository is the complete backend: custom tables plus the auth tables. Key tables:

| Table | Purpose |
|---|---|
| `profiles` | User profiles and roles |
| `cmd_drones` | Drones paired to an account |
| `cmd_pairingRequests` | Pairing-code requests |
| `cmd_droneStatus` | Status posted by agents through the relay |
| `cmd_droneCommands` | Command queue (Mission Control enqueues, the agent polls) |
| `cmd_missions` | Missions synced across devices |
| `cmd_preferences` | Preferences synced across devices |
| `cmd_flightLogs` | Synced flight records |
| `cmd_mcpTokens` | MCP credentials (only a hash is stored) |
| `cmd_signingKeys` | MAVLink signing key records |
| `cmd_pluginInstalls` | Extension installs per drone |
| `registry_plugins`, `registry_versions` | The extension registry |
| `community_changelog` | Changelog entries |
| `contactSubmissions` | Contact form submissions |

## Offline behaviour

- Local connections keep working when the network drops.
- Settings stay in the browser's storage.
- Previously loaded fleet data stays visible and is marked stale.
- Mission Control retries the backend in the background.

For field work without internet, use USB or LAN connections. The cloud adds remote reach and sync; it is never required to fly.
