This page lists every built-in tool the [ADOS MCP server](/developers/mcp-server) registers: 45 tools in 12 groups, from catalog version `0.1.0` against MCP revision `2025-06-18`. The data comes from `catalog/tools-catalog.json` (scope, safety class, reach flags, description) and the Zod input schemas in `src/registry/read-tools.ts`, `src/registry/admin-tools.ts` and `src/registry/flight-tools.ts` (arguments). Mission Control renders the same catalog in the MCP tab's **Built-in tools** section.

To connect a client first, see [Connect an AI assistant](/mission-control/mcp-setup).

<Note>
A client never sees this whole list unless its credential allows it. `tools/list` is filtered per connection: a tool appears only when the token holds its scope, flight-affecting tools stay hidden until flight enforcement is on, and agent-mode-only tools are hidden in fleet-mode.
</Note>

## Reading the tables

| Column | Meaning |
|---|---|
| Scope | The scope group the token must hold to call the tool. The server checks it on every call. |
| Safety class | The class-specific gate the call passes after the scope check. See [Safety classes](#safety-classes). |
| Agent-mode only | The tool is served only over the drone-direct reach (`--target agent` or `--target local-fleet`). The cloud relay has no synchronous parameter or config read/write, no plugin install or plugin config, and no supervisor restart, so in fleet-mode these tools are hidden from `tools/list` and refused with `agent_mode_only`. |
| Affects flight | The tool writes MAVLink or changes in-flight behaviour. It is hidden and refused until the server runs with `--flight-enforced`, and never reaches a token without the `flight` scope. |

In the argument tables, the description is the one declared in the schema; a dash means the schema declares none. Integer arguments without a listed range accept any safe integer. Every tool's schema rejects unknown properties (`additionalProperties: false`).

## Scopes

A scope is a named group, not a single permission. A token carries one or more groups, and each tool requires exactly one. The groups line up one-to-one with the safety classes, except `secret_read`, which is a modifier on reads rather than a class.

| Scope | Default | Grants |
|---|---|---|
| `read` | On | Status, telemetry, parameters, configuration, logs and the audit log. No changes. |
| `safe_write` | On | Reversible writes, such as one config value or one plugin config value. |
| `admin` | On | Node administration: services, plugins, pairing, radio and network settings, parameter writes. |
| `flight` | Off | Commands that move the aircraft: arm, disarm, takeoff, land, RTL, mode. |
| `destructive` | Off | Irreversible actions such as reboot, shutdown, factory reset and reset-all-parameters. No built-in tool in this release is `destructive`. |
| `secret_read` | Off | Return secret-bearing values unredacted. Requires `read`; a token cannot hold it alone. |

"Default" is the scope set the server marks as on by default (`read`, `safe_write` and `admin`), which is also what Mission Control's default **Operate** preset grants. `flight`, `destructive` and `secret_read` are elevated and must be added explicitly.

## Safety classes

The scope check decides whether a token may call a tool. The safety gate then decides whether this particular call goes through. It runs for every principal, including the on-box Unix socket caller, which skips only the scope check.

| Class | What the call must carry |
|---|---|
| `read`, `safe_write` | Nothing beyond the scope. |
| `admin` | `confirm: true` in the arguments. Without it the call is refused with `confirm_required`. |
| `flight` | One of: a one-time operator signed confirm in `confirm_id`, bound to this tool, node and exact arguments; a fresh operator-present signal (no older than 10 seconds); or a target verified as SITL with `--sim`. |
| `destructive` | The exact typed confirm phrase in `confirm` (for example `RESET ALL PARAMS ON THIS NODE`) and an operator signed confirm in `confirm_id`. `--sim` waives the signature, never the phrase. |

Some tools escalate from their base class at call time based on their arguments: `params.set`, `config.set` and `services.restart`. The rules are listed with each group below.

<Warning>
The server's entry point (`src/index.ts`) starts the gate without an operator-present or signed-confirm provider, so both default to "absent". On real hardware every `flight` class call is refused today; flight tools only run against a simulator started with `--sim`, which the server verifies against the target before it arms the waiver. Treat flight access as a SITL feature until a confirm provider ships.
</Warning>

Tool annotations (`readOnlyHint`, `openWorldHint`) are advertised honestly, but they are hints for the client. The server is the enforcement point.

## Common arguments

| Argument | Used by | Meaning |
|---|---|---|
| `node` | Every tool except `fleet.list_nodes` and `audit.search` | The target node. In agent mode the server always targets its one node: omit `node`, or pass `local` or the node's device id (`--node-id`); any other value is refused with `node_not_allowed`. In local-fleet mode pass a device id from the fleet; it can be omitted only when the fleet has one node. In fleet-mode it is required and must be a node the credential may reach (its allowed nodes, or any node you own when the credential has no node limit). For `audit.query` it is a filter, not a target. |
| `confirm` | `admin` class tools | Set `true` to confirm the administrative action. |
| `confirm_id` | Flight tools, and admin tools that declare it | A signed, one-time confirm id bound to this tool, node and arguments. Needed when the call runs through the flight gate. |

## Plugin tools

Besides the built-in tools, the server discovers MCP tools contributed by extensions installed on a node and registers them as `<pluginId>:<toolName>`. They are not in the catalog because they depend on what is installed. The rules:

- A plugin's tools are exposed only if the plugin holds the `mcp.expose` capability, and only its agent-half tools are registered.
- The declared `safety_class` maps to a scope: `read`, `safe_write`, `admin`, `flight` (also spelled `flight_action`) or `destructive`. A missing or unknown class maps to `admin`.
- The class is floored at what the plugin's granted capabilities imply, so a plugin holding a flight-capable capability has every tool treated as `flight`, whatever it declares.
- Plugin tools are always agent-mode only. A destructive plugin tool's typed phrase is `CONFIRM <PLUGINID:TOOLNAME>` in upper case.
- The advertised description is capped at 512 characters and an input schema larger than 16 KiB is dropped from `tools/list`. The plugin validates its own arguments.

See [Manifest reference](/developers/manifest) for how an extension declares MCP tools.

| `flight.rtl` | `flight` | `flight` | No | Yes | Return to launch. Requires the flight scope and an operator-present or signed confirm (or --sim). |
| `flight.takeoff` | `flight` | `flight` | No | Yes | Takeoff to an altitude AGL in metres. Requires the flight scope + confirm/sim. |

Only the six commands the agent's `/api/command` accepts are registered. `flight.goto`, `flight.emergency_stop` and the mission upload and clear tools have rows in the server's route table but no reachable agent endpoint yet, so they are not registered: Planned.

A flight result reports what the flight controller did, not just delivery. The agent answers HTTP 200 even when the flight controller rejects a command, so the tool returns `ok: true` only when the `COMMAND_ACK` was accepted. The result also carries `cmd`, `delivered`, `acked`, `accepted`, and, when present, `result` (the ACK result name), `reason` (the flight controller's status text), `message` and `raw`.
