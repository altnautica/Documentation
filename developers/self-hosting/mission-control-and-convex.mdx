Mission Control is a Next.js app you can build into a single Docker image and
run on your own host. It talks to a Convex backend for sign-in, fleet
management and the cloud command queue. Both halves live in
[ADOSMissionControl](https://github.com/altnautica/ADOSMissionControl) under
GPL-3.0: the root `Dockerfile` builds the GCS, and `convex/` holds the
functions and schema you push to the backend.

<Note>
You do not need Convex to fly on the LAN. Served over plain HTTP, Mission
Control connects straight to the agent and pairs over the local network with no
backend. Convex is for the cloud relay (cross-network access) and for auth.
</Note>

## The two Convex origins

A self-hosted Convex backend exposes two origins that are not
interchangeable:

- The **client API** origin (`:3210`) serves the GCS browser bundle
  (`NEXT_PUBLIC_CONVEX_URL`) and every `npx convex deploy` and
  `npx convex env set` call.
- The **site** origin (`:3211`) serves HTTP actions: the agent heartbeat and
  pairing (`server.self_hosted.url`, `pairing.convex_url`) and the broker auth
  sync.

Cross the two and the GCS loads but no drone ever appears, or sign-in works
while commands never reach the agent. All published ports are in the
[port table](/developers/self-hosting/troubleshooting-and-ports#ports).

## Build and run the GCS image

The `Dockerfile` is a multi-stage build that produces a Next.js standalone
server listening on port `4000`. `NEXT_PUBLIC_*` values are inlined at build
time, so pass the Convex client API origin the browser will reach as a build
argument.

<Steps>
  <Step title="Build the image">
    ```bash
    cd ADOSMissionControl
    docker build \
      --build-arg NEXT_PUBLIC_CONVEX_URL=https://convex.cloud.example.com \
      -t ados-mission-control .
    ```

    Build arguments the `Dockerfile` accepts:

    | Build arg | Purpose |
    |---|---|
    | `NEXT_PUBLIC_CONVEX_URL` | Convex client API origin (`:3210`). Required for cloud mode. |
    | `NEXT_PUBLIC_CESIUM_ION_TOKEN` | 3D terrain tiles. Optional. |
    | `NEXT_PUBLIC_DEMO_MODE` | `true` ships the build with the demo fleet. |
    | `NEXT_PUBLIC_PLUGIN_REGISTRY_URL` | Plugin registry origin. Optional. |
    | `ADOS_MANIFEST_URL` | Agent install manifest origin. Optional. |
    | `NEXT_PUBLIC_ANALYTICS_SCRIPT_URL` | Analytics script URL. Optional. |
    | `NEXT_PUBLIC_ANALYTICS_WEBSITE_ID` | Analytics site ID, used with the script URL. Optional. |
  </Step>
  <Step title="Run the container">
    ```bash
    docker run -d \
      --name ados-mission-control \
      -p 4000:4000 \
      ados-mission-control
    ```

    The GCS is now at `http://localhost:4000`. The container sets `PORT=4000`
    and `HOSTNAME=0.0.0.0`; map `-p` to any host port you want.
  </Step>
</Steps>

<Tip>
Cloud mode (relay through Convex and MQTT) only activates when the GCS is
served over HTTPS. Over plain HTTP the GCS stays local and connects directly to
agents on the LAN. Put the container behind a TLS proxy or a
[Cloudflare tunnel](/developers/self-hosting/all-in-one#expose-the-stack-through-a-cloudflare-tunnel)
to reach a drone across networks.
</Tip>

## Stand up a self-hosted Convex backend

You have two routes:

- **Convex Cloud** is a hosted backend. In the `ADOSMissionControl` directory
  run `npx convex dev` to create and link a deployment, then
  `npx @convex-dev/auth` to set up its auth keys.
- **Self-hosted** runs the open-source backend image
  [`ghcr.io/get-convex/convex-backend`](https://github.com/get-convex/convex-backend)
  in Docker. The rest of this page covers that route.

The [all-in-one stack](/developers/self-hosting/all-in-one) bundles the backend
with its dashboard, the GCS and the relay layers in one compose file. To run
the backend on its own:

<Steps>
  <Step title="Start the backend">
    Start the `convex-backend` service from the all-in-one compose file, or
    your own compose file using the same image:

    ```bash
    docker compose up -d convex-backend
    ```
  </Step>
  <Step title="Generate the admin key">
    ```bash
    docker compose exec convex-backend ./generate_admin_key.sh
    ```

    Store the key in a secrets manager. The commands below use it as
    `<admin-key>`.
  </Step>
  <Step title="Push functions and schema">
    From a machine with the repo checked out, point the CLI at your own
    client API origin and admin key:

    ```bash
    cd ADOSMissionControl
    npx convex deploy \
      --url https://convex.cloud.example.com \
      --admin-key <admin-key>
    ```

    <Warning>
    On a self-hosted backend every Convex CLI call needs your own `--url` and
    `--admin-key`. Without them the functions land on another deployment and
    sign-in fails with no visible error.
    </Warning>
  </Step>
  <Step title="Generate the auth keys">
    A fresh backend has no signing keys. Convex Auth signs session JWTs with
    RS256. The helper script prints `JWT_PRIVATE_KEY` and `JWKS` lines;
    evaluate them into your shell:

    ```bash
    eval "$(node scripts/generate-auth-keys.mjs | grep -E '^(JWT_PRIVATE_KEY|JWKS)=')"
    ```
  </Step>
  <Step title="Set the auth environment">
    Set the keys plus the GCS origin. `SITE_URL` is the origin the browser
    loads the GCS from, not a Convex origin:

    ```bash
    npx convex env set JWT_PRIVATE_KEY "$JWT_PRIVATE_KEY" \
      --url https://convex.cloud.example.com --admin-key <admin-key>

    npx convex env set JWKS "$JWKS" \
      --url https://convex.cloud.example.com --admin-key <admin-key>

    npx convex env set SITE_URL "https://gcs.cloud.example.com" \
      --url https://convex.cloud.example.com --admin-key <admin-key>
    ```
  </Step>
</Steps>

## Relay environment on Convex

Convex carries auth, fleet state and the cloud command queue. Live telemetry
and browser video go through the MQTT broker and the video relay, and Convex
needs four values for them:

```bash
# Public broker WebSocket URL the GCS connects to
npx convex env set MQTT_BROKER_URL "wss://mqtt.cloud.example.com" \
  --url https://convex.cloud.example.com --admin-key <admin-key>

# Public video relay URL the GCS opens streams on
npx convex env set VIDEO_RELAY_URL "wss://video.cloud.example.com" \
  --url https://convex.cloud.example.com --admin-key <admin-key>

# Signs five-minute viewer tokens; same value as the relay's VIDEO_RELAY_SECRET
npx convex env set VIDEO_RELAY_SECRET "<openssl rand -hex 32>" \
  --url https://convex.cloud.example.com --admin-key <admin-key>

# Bearer the broker auth sync presents; same value as in the broker's env
npx convex env set MQTT_AUTH_RELAY_SECRET "<openssl rand -hex 32>" \
  --url https://convex.cloud.example.com --admin-key <admin-key>
```

Without `VIDEO_RELAY_SECRET` the GCS reports the relay as not configured.
Without `MQTT_AUTH_RELAY_SECRET` the broker credential endpoint answers `503`
and no device can log in to the broker.

## Point the agent at the backend

Set the drone's `server.mode` to `self_hosted` and point both
`server.self_hosted.url` and `pairing.convex_url` at the site origin
(`:3211`). The full procedure is on
[Self-hosting: Drone Agent](/developers/self-hosting/agent).

## Verify

- `curl https://convex.cloud.example.com/version` returns a version, so the
  backend answers on the client API origin.
- Sign-in works in the GCS, so the auth keys are on the right deployment.
- A paired drone appears in the fleet, so its heartbeat reached the site
  origin.

Over plain HTTP the GCS stays local; serve it behind TLS to use the cloud
relay. If the GCS loads but no drone appears, recheck the `:3210` versus
`:3211` wiring above.
