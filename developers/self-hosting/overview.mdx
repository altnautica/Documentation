ADOS is open source end to end, and you can run the whole stack on hardware
you own. This page maps what is self-hostable, how the pieces connect, and
the routes to bringing the cloud relay up.

## Local-first by default

You do not need any cloud infrastructure to fly. The default path is local,
over your LAN:

- The drone-to-ground link is the WFB-ng radio.
- Mission Control reaches an agent directly by hostname or IP. Paste the
  agent's address into the Add-a-Node card and the GCS pairs with it over the
  LAN. No Convex round-trip is involved.

A fresh agent install runs with `server.mode: local`, and nothing reaches out
to a backend. That is the correct setup for a single-LAN bench or field
deployment.

<Note>
On the LAN, Mission Control talks to the agent over plain HTTP. The cloud
relay path is used only when the GCS is served over HTTPS. See
[Drone Agent configuration](/drone-agent/configuration) for the agent's
`server` block.
</Note>

## When you want the cloud relay

The cloud relay is the opt-in path for reaching a drone across networks:
remote sites, mobile data, anywhere the GCS and the agent are not on the same
LAN. Each layer is optional.

| Layer | What it carries |
|---|---|
| Convex backend | Auth, fleet records, cloud commands, and the agent's status heartbeat. |
| MQTT broker | The live MAVLink and MSP byte planes, WebRTC signaling, vision detections and plugin streams between the agent and the browser. |
| Video relay | Live video in the browser, remuxed from RTSP with no transcoding. |

Fleet status does not travel over MQTT. The agent POSTs its status heartbeat
straight to `{convex}/agent/status` over HTTPS every 5 seconds, authenticated
with its `X-ADOS-Key`. The broker carries the live data planes under
`ados/<deviceId>/...`; the full topic list is on
[Cloud infrastructure](/architecture/cloud-infrastructure).

To put an agent on a self-hosted backend, set its `server.mode` to
`self_hosted`, point `server.self_hosted.url` and `pairing.convex_url` at your
Convex site origin, and set `server.self_hosted.mqtt_broker` to your broker.
See [Self-hosting: the agent](/developers/self-hosting/agent).

To run only the layers you need, the broker and the video relay each ship
their own compose file under `tools/mqtt-bridge/deploy/` and
`tools/video-relay/deploy/`, so you can add a relay layer beside an existing
Convex deployment.

## Convex has two origins

A self-hosted Convex backend exposes two origins that are not
interchangeable:

- **`:3210`** is the client API. The Mission Control browser bundle talks to it
  (`NEXT_PUBLIC_CONVEX_URL`), and `npx convex deploy` pushes functions to it.
- **`:3211`** is the site origin that serves HTTP actions. The agent's pairing
  register, status heartbeat and command poll go here, and so does the broker
  auth sync. The agent's `server.self_hosted.url` and `pairing.convex_url`
  point here.

Cross the two and the GCS loads but no drone ever appears. Every port in the
stack is listed on
[Self-hosting: ports and troubleshooting](/developers/self-hosting/troubleshooting-and-ports).

## Resource footprint

A small deployment of one to five drones runs on a single 4-core, 8 GB Linux
host that runs Convex, Mosquitto and the video relay together. The Convex
backend needs the most headroom, because its SQLite store grows with your data.
The broker is light. The video relay runs one ffmpeg remux per stream that has
viewers.

| Component | Bandwidth |
|---|---|
| Convex (self-hosted) | Under 1 GB/month |
| Convex (hosted) | Under 1 GB/month |
| MQTT relay | About 100-500 MB/month per drone |
| Cloudflare Tunnel | No limit applied by the tunnel |
| STUN | Negligible |
| Video (peer-to-peer WebRTC) | None through your server |
