description: "Every key a plugin can declare under gcs.contributes: what it adds to Mission Control, its manifest shape, where it renders and the capability it needs."
---

A plugin's `contributes` block is how it adds surfaces to Mission
Control. The GCS half declares them under `gcs.contributes`; the agent
half declares its own (`services`, `shared_topics`, `drivers`, `vision`
and the MCP lists) under `agent.contributes`, described in the
[manifest reference](/developers/manifest#agent). This page is the
reference for the GCS-side keys.

Every contribution is **declarative**. You name what you want in
`manifest.yaml`, request the matching capability, and the host mounts
it. There is no runtime "register this panel" call.

<Note>
Each visual contribution needs the matching `ui.slot.*` capability under
`gcs.permissions`. A contribution whose slot capability was not granted
is not mounted: the slot skips it and shows the operator a notice naming
the missing grant. See [Permissions](/developers/permissions).
</Note>

## The shape of `contributes`

```yaml
gcs:
  entrypoint: "gcs/plugin.bundle.js"
  isolation: iframe
  permissions:
    - id: ui.slot.flight-skill
    - id: ui.slot.node-detail-tab
    - id: ui.slot.video-overlay
    # ... one ui.slot.* per visual surface you mount
  contributes:
    skills: []             # cockpit Skill Bar entries
    target_actions: []     # actions on a clicked detection in the cockpit
    tabs: []               # node.detail.tab on any node profile
    parameters: []         # native schema-driven form fields
    settings: []           # sections of native parameters
    panels: []             # an iframe in the slot each entry names
    overlays: []           # video.overlay
    notifications: []      # notification.channel
    mission_templates: []  # mission.template entries
    map_overlays: []       # map.overlay entries
    models: []             # vision model registrations
    agent_pages: []        # pages in a node's Agent sidebar
    node_surfaces: []      # top-level tabs on a node's detail panel
    tools: []              # MCP tools (schema 3)
    resources: []          # MCP resources (schema 3)
    prompts: []            # MCP prompts (schema 3)
  locales:
    - en
```

Keys are snake_case. Mission Control also reads `missionTemplates`,
`mapOverlays` and `targetActions`, but the agent's validator (and so
`ados plugin lint`, `sign` and `test`) rejects the camelCase spelling.

Omit the arrays you do not need. Mission Control parses each array
independently and drops a malformed entry with a console warning rather
than failing the whole plugin. The `tools`, `resources` and `prompts`
lists are covered in the
[manifest reference](/developers/manifest#schema-3-fields-mcp-tools-resources-and-prompts).

## Slot and capability map

| `contributes` key | Slot | Capability | Renders in |
|-------------------|------|------------|------------|
| `skills` | `flight.skill` | `ui.slot.flight-skill` | The cockpit Skill Bar |
| `target_actions` | (no slot) | none | The cockpit target popup, on a clicked detection |
| `tabs` | `node.detail.tab` | `ui.slot.node-detail-tab` | A node's detail panel (any profile) |
| `panels` | the entry's `slot` | the slot's `ui.slot.*` | Wherever that slot renders (see below) |
| `settings` | `settings.section` | `ui.slot.settings-section` | The Settings page, native form |
| `overlays` | `video.overlay` | `ui.slot.video-overlay` | Above the live video in the cockpit |
| `map_overlays` | `map.overlay` | `ui.slot.map-overlay` | The flight and planner maps |
| `notifications` | `notification.channel` | `ui.slot.notification-channel` | Mission Control notifications |
| `mission_templates` | `mission.template` | `ui.slot.mission-template` | The planner's pattern editor |
| `models` | (no slot) | none on the GCS half | The model picker and the agent's vision engine |
| `agent_pages` | `node.agent.page` | `ui.slot.node-agent-page` | A node's Agent sidebar, in the section the entry names |
| `node_surfaces` | `node.surface` | `ui.slot.node-surface` | A top-level tab on the node detail panel, for the profiles the entry names |

### The slot taxonomy

There are 13 slots. Each maps one-to-one to its capability by replacing
dots with dashes: `node.detail.tab` needs `ui.slot.node-detail-tab`.

| Slot | Scope | Where it renders |
|------|-------|------------------|
| `fc.tab` | Fleet | A tab in a drone's **Setup** tab |
| `hardware.tab` | Fleet | The **Extensions** section of a node's System tab and of the ground station Peripherals tab |
| `settings.section` | Fleet | The **Extensions** section of the Settings page |
| `mission.template` | Fleet | The planner's pattern editor |
| `map.overlay` | Fleet | The flight map and the planner map |
| `video.overlay` | Fleet | Above the live video in the cockpit |
| `notification.channel` | Fleet | Mission Control notifications |
| `node.detail.tab` | Per drone | A node's detail panel |
| `cockpit.panel` | Per drone | The cockpit quick-settings surface |
| `cockpit.widget` | Per drone | A widget in a cockpit corner zone over the live video |
| `flight.skill` | Per drone | The cockpit Skill Bar (no iframe) |
| `node.agent.page` | Per drone | A node's Agent sidebar |
| `node.surface` | Per drone | A top-level node-detail tab |

A per-drone contribution is bound to the selected drone: its capability
token names that drone, and it is torn down and re-mounted when the
operator switches drone. The node-scoped slots are the six marked per
drone; the other seven are fleet-level.

## skills

A **Skill** is a flight behavior that surfaces in the cockpit Skill
Bar. It can be bound to a hotkey or a gamepad button, toggled or fired
once, and gated on arm state. Built-in commands and plugin behaviors
such as Follow-Me are the same Skill shape.

**What it does.** Registers an entry in the Skill Bar. Activation writes
a key in the plugin's per-drone config (`activation.via: config`); the
plugin's agent half reads that key and starts or stops the behavior. The
Skill's live state is read back from an event topic (`state.via:
event`), so the bar shows what the plugin reports rather than an
optimistic guess.

```yaml
contributes:
  skills:
    - id: follow-me
      label: "Follow-Me"
      icon: "crosshair"             # lucide-react icon name
      category: behavior            # behavior | camera | navigation | utility
      toggle: true                  # on/off toggle, or one-shot when false
      confirm: false                # ask the operator to confirm before activation
      arm_requirement: armed        # any | armed | disarmed
      default_binding:
        key: "f"                    # suggested hotkey
        gamepad_button: 3           # optional suggested gamepad button
      activation:
        via: config                 # the only activation transport
        config_key: active          # the per-drone config key activation writes
      state:
        via: event                  # the only state transport
        topic: "follow.state"       # the event topic the bar reads back
```

**Where it renders.** The cockpit Skill Bar. The operator rebinds it in
**Settings → Input Devices**.

**Capability.** `ui.slot.flight-skill`.

<Warning>
Mission Control honors only `activation.via: config` and
`state.via: event`, and both `config_key` and `topic` must be set. A
skill entry with any other transport is dropped. The Skill only triggers
the plugin's behavior: the agent half still needs its own flight
capabilities (`mavlink.write`, `flight.guided_setpoint`) to act, and the
cockpit's arm and confirm gates still apply. See
[Safety](/operations/safety).
</Warning>

## target_actions

A **target action** is an action a plugin offers on a detection the
operator clicks in the cockpit video. It appears in the same popup as
the built-in actions, and can be fired on the selected target with a
key.

**What it does.** When the operator picks the action, Mission Control
optionally designates the clicked box to the drone's vision tracker,
then writes one key of the plugin's per-drone config so the agent half
reacts.

```yaml
contributes:
  target_actions:
    - id: follow
      label: "Follow this target"
      icon: crosshair
      order: 20                     # position in the popup, lower first
      applies_to_class: person      # optional: offer only on this class
      designate: true               # designate the box before the config write
      config_key: active            # the per-drone config key to write
      config_value: true            # the value written (default true)
      default_key: "f"              # optional key that fires it on the selected target
```

An action that writes the same `config_key` as one of the plugin's
skills inherits that skill's confirm and arm gates, so the two surfaces
cannot bypass each other. An action that writes `false` is a stop and is
not gated. A `default_key` that collides with a chord Mission Control
owns is ignored.

**Where it renders.** The cockpit target popup on a clicked detection.

**Capability.** None on the GCS half: Mission Control performs the
designation and the config write itself. The agent half needs the
vision capabilities to see detections (`vision.detection.subscribe`)
and its flight capabilities to act on them.

## tabs

A **node-detail tab** mounts on a node's detail panel. It works on any
node profile. Use it for a configuration or status surface that belongs
to one node.

**What it does.** Adds a tab to the selected node's detail panel,
rendered as a sandboxed iframe scoped to that node. An optional
`profile` list narrows which node profiles offer the tab.

```yaml
contributes:
  tabs:
    - id: follow-me-tab
      title: "Follow-Me"
      icon: "crosshair"
      order: 70                     # sort hint in the tab strip
      profile: ["drone"]            # optional: drone | ground-station | workstation | compute
```

**Where it renders.** The node detail panel, in the tab strip, when the
node profile matches. With no `profile` the tab is offered on every
profile.

**Capability.** `ui.slot.node-detail-tab`.

<Note>
The entry accepts `id` or `key` as its stable id. A `tabs` entry always
resolves to the `node.detail.tab` slot; any `slot` field on it is
ignored.
</Note>

## parameters

A **parameter** is a native, schema-driven form field Mission Control
renders itself, with no iframe. The plugin declares the field's type,
bounds and widget; the host renders the control, validates and clamps
the value, and writes it to the binding you name.

```yaml
contributes:
  parameters:
    - key: standoff_distance_m
      schema:
        type: number
        minimum: 2
        maximum: 60
        step: 0.5
        default: 8
      ui:
        widget: range
        label: "Standoff distance"
        group: "Follow"
        help: "How far behind the subject to hold, in meters."
      binding: plugin.config
```

**Where it renders.** The plugin's parameter panel on the node detail
panel and in the cockpit quick-settings surface, grouped by `ui.group`
and ordered by `ui.order`.

**Capability.** No `ui.slot.*` for the native form itself. A parameter
bound to `engine.detector` switches the shared vision detector.

The schema, the widget set, `visible_if` and the bindings are on the
[parameter schema reference](/developers/parameter-schema).

## settings

A **settings section** groups native parameters under a heading. Use it
when a plugin has more than a handful of parameters.

```yaml
contributes:
  settings:
    - id: follow-tuning
      title: "Follow tuning"
      icon: "sliders"
      order: 10
      parameters:
        - key: standoff_distance_m
          schema: { type: number, minimum: 2, maximum: 60, step: 0.5, default: 8 }
          ui: { widget: range, label: "Standoff distance" }
        - key: standoff_height_m
          schema: { type: number, minimum: 2, maximum: 40, step: 0.5, default: 6 }
          ui: { widget: range, label: "Standoff height" }
```

**Where it renders.** The **Extensions** section of the Settings page.
Sections are ordered by `order`.

**Capability.** `ui.slot.settings-section`.

## panels

A **panel** mounts the plugin's iframe bundle into the slot each entry
names. Unlike `tabs`, which always resolve to `node.detail.tab`, a panel
can target any iframe slot.

```yaml
contributes:
  panels:
    - id: power-tab
      slot: fc.tab                  # any iframe slot from the taxonomy
      title: "Power"
      icon: "zap"
      order: 30
    - id: link-widget
      slot: cockpit.widget
      title: "Link"
      zone: top-right               # cockpit.widget only: top-left | top-right | bottom-left | bottom-right
```

**Where it renders.** In the named slot; see
[the slot taxonomy](#the-slot-taxonomy). The common choices are
`fc.tab` (a tab in a drone's **Setup** tab), `hardware.tab`,
`settings.section` (an iframe section; use `settings` for a native
one), `cockpit.panel` and `cockpit.widget` (default zone
`bottom-left`).

**Capability.** The `ui.slot.*` capability of the slot you name, for
example `ui.slot.fc-tab` or `ui.slot.cockpit-widget`.

## overlays

A **video overlay** draws on top of the live video. Use it for detection
boxes or a HUD.

**What it does.** Mounts the plugin's iframe above the video player,
letterbox-corrected so plugin geometry lines up with the video pixels.
For vector marks (boxes, reticles, labels) the bridge's `cockpit.marks`
method composites them into one shared layer instead.

```yaml
contributes:
  overlays:
    - id: follow-me-overlay
      title: "Follow-Me"           # optional
      icon: "crosshair"            # optional
      order: 50                    # optional
```

An `overlays` entry implies the `video.overlay` slot.

**Where it renders.** Above the live video in the cockpit.

**Capability.** `ui.slot.video-overlay`.

## notifications

A **notification channel** lets the plugin push alerts into Mission
Control.

**What it does.** Registers a named channel. The GCS half publishes into
it with `ctx.notifications.publish`; messages appear as toasts.

```yaml
contributes:
  notifications:
    - id: battery-anomaly
      title: "Battery anomaly"
      icon: "battery-warning"      # optional lucide-react icon
      order: 20                    # optional sort hint
```

A `notifications` entry implies the `notification.channel` slot.
Mission Control reads only `id`, `title`, `icon` and `order` from the
entry. Severity is set per message on the `ctx.notifications.publish`
payload (`info`, `warning`, `error`, `success` or `critical`).

**Capability.** `ui.slot.notification-channel`.

## mission_templates

A **mission template** adds an entry to the planner's pattern editor.

```yaml
contributes:
  mission_templates:
    - id: corridor-survey
      title: "Corridor Survey"
      icon: "route"
```

**Where it renders.** The planner's pattern editor.

**Capability.** `ui.slot.mission-template`.

<Note>
A template only registers the entry. A mission built from it goes
through the normal pre-upload validation and operator approval before it
reaches the aircraft.
</Note>

---

## map_overlays

A **map overlay** draws on the map: polygons, markers or heatmaps.

```yaml
contributes:
  map_overlays:
    - id: coverage-heatmap
      title: "Coverage"
      icon: "map"
```

**Where it renders.** The flight map and the planner map, as a layer
above the base map.

**Capability.** `ui.slot.map-overlay`.

## models

A **model registration** adds a vision model to the catalog the agent's
vision engine selects from, with per-board variants. Use it when a
plugin ships its own detector rather than relying on the built-in
catalog.

**What it does.** Registers a model id for a vision task with one or
more per-board variants. The agent selects the variant whose
`board_match` fits the running board, downloads it from `source`, and
verifies it against `sha256`. A `model` parameter then lets the operator
switch the active detector.

```yaml
contributes:
  models:
    - id: coco-yolov8n
      task: detection
      board_variants:
        - board_match: "rk3588"     # SoC or board substring
          runtime: "rknn"           # inference runtime the variant targets
          input: "640x640"          # input resolution hint
          min_tops: 3               # minimum NPU throughput needed
          source: "https://example.com/models/coco-yolov8n-rk3588.rknn"
          sha256: "<sha256 of the .rknn file>"
        - board_match: "cpu"
          runtime: "onnx"
          input: "640x640"
          source: "https://example.com/models/coco-yolov8n.onnx"
          sha256: "<sha256 of the .onnx file>"
```

**Where it renders.** No slot of its own. The model shows up in the
picker a `model` parameter renders, and feeds the agent's vision engine.

**Capability.** None on the GCS half. The agent half needs the vision
capabilities that consume it (`vision.frame.read`,
`vision.detection.subscribe`), and a `model` parameter must bind to
`engine.detector` to switch the active detector.

## agent_pages and node_surfaces

These two put a plugin's pages where the built-in node pages live,
rather than in a generic plugin tab. Both are rendered from the GCS
bundle, so they need `gcs.entrypoint`.

```yaml
gcs:
  permissions:
    - id: ui.slot.node-agent-page
    - id: ui.slot.node-surface
  contributes:
    agent_pages:
      - { id: survey, title: "Survey", section: videoVision, profile: [drone] }
      - { id: survey-setup, title: "Survey setup", setup_for: survey, profile: [drone] }
      - { id: survey-live, title: "Live survey", section: videoVision, after: survey, profile: [drone] }
    node_surfaces:
      - { id: overview, title: "Survey", profile: [workstation, compute], group: status, order: 10 }
```

`agent_pages[]`:

| Field | Required | Notes |
|-------|----------|-------|
| `id` | yes | `[a-z0-9][a-z0-9_-]{0,63}`, unique in the list. |
| `title` | yes | 1 to 80 printable characters. |
| `icon` | no | An icon name. |
| `section` | no | The sidebar section: `node`, `radioLink`, `networking`, `fleet`, `videoVision`, `cloud`, `system` or `software`. An unknown section falls back to `software`. |
| `after` | no | Place the page after this page id when the section has it. |
| `order` | no | Order among plugin pages when `after` does not apply. |
| `profile` | no | Node profiles the page appears on. Absent means every profile. |
| `setup_for` | no | The id of another page of this plugin. The page then renders as that page's Setup segment instead of a row of its own. It cannot name itself or another setup page. |

`node_surfaces[]`:

| Field | Required | Notes |
|-------|----------|-------|
| `id` | yes | `[a-z0-9][a-z0-9_-]{0,63}`, unique in the list. |
| `title` | yes | 1 to 80 printable characters. The tab label. |
| `profile` | yes | Node profiles the tab appears on. At least one. |
| `group` | no | `status`, `vehicle`, `link`, `device` or `compute`. The tab lands at the end of that group's run, or just before the Agent tab when the node has no such group. |
| `order` | no | Order among plugin tabs. |
