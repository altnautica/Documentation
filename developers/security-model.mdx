A plugin runs third-party code next to a flying vehicle. Every plugin is
sandboxed, every privileged call is gated by a capability the operator
granted, and every archive is signed and checked before a file lands on
disk.

This page is the threat-model summary: what each half can reach, what it
cannot, and the worst case if a plugin turns out to be malicious or
buggy. The mechanics live in [Concepts](/developers/concepts),
[Permissions](/developers/permissions), the
[agent plugin deep dive](/developers/agent-plugin-deep-dive) and the
[GCS plugin deep dive](/developers/gcs-plugin-deep-dive).

## The two sandboxes at a glance

| | Agent half | GCS half |
|---|---|---|
| Where it runs | The drone or ground station node, as its own systemd unit | The Mission Control browser, in an iframe |
| Language | Python (`ados.sdk`) or Rust (`ados-sdk`) | TypeScript (`@altnautica/plugin-sdk`) |
| Isolation primitive | Per-plugin system user, hardened unit, `ados-plugins.slice` cgroup | `<iframe sandbox="allow-scripts">` on a `blob:` document, null origin |
| Host channel | Unix domain socket, length-prefixed msgpack | `postMessage` |
| Resource cap | `MemoryMax`, `CPUQuota`, `TasksMax` from the manifest | Browser tab limits |
| Network | None unless granted `network.outbound`; node-local addresses always blocked | None: the frame CSP has `connect-src 'none'` |
| Privilege gate | Capability token checked on every IPC call | Capability re-resolved and checked on every bridge call |

## Agent half: what it can and cannot do

Each agent half runs as a generated systemd unit inside
`ados-plugins.slice`, under its own system user `ados-plg-<hash8>` in
the `ados-plugins` group. There is no in-process mode. Every unit
carries these directives:

```ini
User=ados-plg-<hash8>
Group=ados-plugins
BindPaths=/var/ados/plugin-data/<id>
TemporaryFileSystem=/run/ados:ro
BindReadOnlyPaths=/run/ados/plugins/<id>
ReadWritePaths=/var/log/ados/plugins
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=yes
LockPersonality=yes
RestrictRealtime=yes
RestrictSUIDSGID=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
ProtectProc=invisible
RestrictNamespaces=yes
SystemCallArchitectures=native
NoExecPaths=/
ExecPaths=/var/ados/plugins/<id> -/lib -/lib64 -/usr/lib -/usr/lib64
DevicePolicy=closed
SocketBindDeny=any
InaccessiblePaths=-/etc/ados/secrets -/etc/ados/plugin-keys -/etc/ados/pairing.json -/etc/ados/config.yaml ...
```

The capability-dependent part of the unit is re-rendered on every grant
and revoke. Without `network.outbound` the unit gets
`RestrictAddressFamilies=AF_UNIX` and `IPAddressDeny=any`; a hardware
grant such as `hardware.i2c` adds the matching `DeviceAllow=` line;
`filesystem.host` adds `/srv /mnt /media /boot` to `ReadWritePaths` and
relaxes `ProtectHome` to read-only. A Python plugin's `ExecPaths` also
includes the agent's Python environment.

| The plugin CAN | The plugin CANNOT |
|---|---|
| Run its own code in its own process, as its own user | Gain new privileges (`NoNewPrivileges=yes` blocks setuid escalation) |
| Reach the host through its IPC socket | See other plugins' sockets or the agent's runtime files (`/run/ados` is an empty read-only tmpfs with only its own socket dir bound in) |
| Write to its own data dir `/var/ados/plugin-data/<id>` and its log | Write anywhere else on disk, read the agent's secrets, keys or config, or execute files outside its install dir and system libraries |
| Use up to its declared RAM, CPU and PID budget | Exceed that budget (the kernel OOM-kills on memory, throttles CPU, refuses new tasks) |
| Call a host method it was granted a capability for | Call one it was not granted (the host replies `capability_denied: <cap>` before the handler runs) |
| Open outbound connections if it was granted `network.outbound` | Open network sockets without that grant, bind a listening port it did not declare, or reach any listener on the node itself |

### The loopback guard

The agent's own services treat a caller on the node as on-box or as a
lifeline peer. A plugin with `network.outbound` must not inherit that
trust. An nftables rule drops every TCP and UDP packet a plugin process
(any user in the `ados-plugins` group) sends to an address local to the
node: loopback, the access-point and USB addresses, link-local, and
every interface address. The exceptions are DNS (port 53) and the
plugin's own declared `listen_ports`. Every plugin unit reloads the rule
before it starts.

If the rule cannot load (for example `nft` is missing), the agent fails
closed: a `network.outbound` grant is refused, a unit that already holds
one is rendered with the no-network sandbox, and `/api/status/full`
reports `"plugin_loopback_guard": "unavailable"`. When the rule is in
place the field reads `"active"`.

### Blast radius if the agent half is malicious

The worst a compromised agent half can do is bounded by its granted
capabilities. With only low-risk grants (`telemetry.read`,
`event.publish`) it can read telemetry and waste its own CPU budget. A
plugin granted the vehicle-moving capabilities is a different matter:
`mavlink.write`, `msp.write`, `flight.guided_setpoint`,
`flight.rate_setpoint` (critical) and `estimator.pose.inject` can each
move the vehicle. That is why they carry a high or critical risk badge
and the operator approves them explicitly. The sandbox keeps a buggy or
hostile plugin from reaching the rest of the node; it does not make a
granted flight-control capability harmless.

## GCS half: what it can and cannot do

The GCS half runs in an iframe with the strictest sandbox that still
allows JavaScript, on a `blob:` document the host builds:

```html
<iframe sandbox="allow-scripts" src="blob:..."></iframe>
```

The frame document carries a CSP with `connect-src 'none'`, and a guard
script removes WebRTC and nested frames, so the iframe has no network
egress at all.

| The plugin CAN | The plugin CANNOT |
|---|---|
| Run JavaScript and render its own UI in the iframe | Read host cookies, `localStorage` or the host DOM (no `allow-same-origin`, so it runs in a null origin) |
| Call the host over `postMessage` for capabilities it was granted | Fetch from any network origin, open a WebSocket or a WebRTC connection |
| Mount into a UI slot it holds the matching `ui.slot.*` grant for | Redirect the parent window (no `allow-top-navigation`) |
| Receive theme variables and apply them to its own root | Open new windows or submit forms (no `allow-popups`, no `allow-forms`) |
| | Get past a missing grant (the host re-resolves the required capability and ignores the one the envelope claims) |

### Blast radius if the GCS half is malicious

A compromised GCS half is trapped in a null-origin iframe that cannot
read the host session, cannot reach any network, and cannot navigate the
parent page. Its only output is `postMessage` envelopes, and the bridge
checks the capability each one actually needs. The damage ceiling is the
set of GCS capabilities the operator granted (for example `command.send`
to its drone, or `mission.write` to edit a plan). Route any network I/O
through the agent half.

## Capability least privilege

Declare the smallest permission set that makes your plugin work, mark
only the load-bearing ones `required: true`, and leave the rest optional
so an operator can run a reduced version. The catalog, the risk levels
and which capabilities are enforced where are on
[Permissions](/developers/permissions); tokens are described in
[Concepts](/developers/concepts#capability-tokens).

## The trust boundary: first-party and third-party signers

Every `.adosplug` is an Ed25519-signed zip, verified before anything is
unpacked.

```text
/etc/ados/plugin-keys/<signer-id>.pem      # enrolled third-party public keys
/etc/ados/plugin-revocations.json          # revoked signer ids and archive digests
```

| Tier | How it is recognized | What it unlocks |
|---|---|---|
| First-party | Signer `altnautica-2026-A` or `altnautica-2026-B`, verified against the key pinned in the agent | `gcs.isolation: inline`, `agent.resources.class: heavy`, and installing an agent half on a host whose service manager has no sandbox (macOS) |
| Trusted third-party | Signature verifies against a key enrolled under `/etc/ados/plugin-keys/`, signer not revoked | Normal install with `subprocess` and `iframe` isolation |
| Unsigned | No signature, or one that does not verify against an enrolled key | Refused, unless the agent runs with `ADOS_PLUGIN_REQUIRE_SIGNED=0`; then it installs with no signer, shown as **UNSIGNED**, and never gets first-party status |

A revoked signer or a revoked archive digest is refused in every mode,
including with signature enforcement relaxed.

First-party status is granted only to the ids on the in-code allowlist,
and only when the archive's signature verifies against the key pinned
in the agent for that id. A key file planted under a first-party name in
`/etc/ados/plugin-keys/` verifies only as a third party. Write access to
`/etc/ados/plugin-keys/` is still root-equivalent trust for third-party
code: whoever can add a key file can make the node accept archives that
key signs, so protect that directory like root.

<Warning>
`isolation: inprocess` (agent) parses but is refused at install for
every plugin, first-party included. `gcs.isolation: inline` runs the GCS
half in Mission Control's own page, outside the iframe sandbox, so it is
first-party only. A third-party archive that declares it is refused at
install.
</Warning>

Signature enforcement can only be relaxed on the agent itself, for a
bench node. The procedure and its limits are in
[Bench install and signing](/developers/signing-keys#bench-install-and-signing).

## The operator install gate

No plugin installs silently. The install is two-stage: the host parses
the archive in memory, verifies the signature and returns a summary (the
requested permissions, the signer and the risk); only after the operator
approves does it unpack, generate the unit and write the install record.
A plugin that never gets past review leaves no trace. The dialog is
described in [Permissions](/developers/permissions#two-stage-install).

Auto-update does not apply a version that asks for new permissions; the
node reports `update_available` with the new permissions, and the
operator reinstalls to approve them. An operator can revoke any granted
capability at any time from Mission Control or with
`ados plugin perms <id> --revoke <cap>`; the host re-mints the plugin's
token at once without it.

## Why each layer exists

The layers are independent. If one fails, the next still holds.

- **Signing** stops a tampered or unknown-origin archive from
  installing. It is the supply-chain wall.
- **The sandbox** (hardened unit plus cgroup, or null-origin iframe plus
  CSP) bounds a plugin that installed but turns out to be buggy or
  hostile. It is the runtime wall.
- **Capabilities** make the plugin's reach explicit and operator-approved.
  They are the authority wall.
- **The install gate** keeps a person in the loop for every grant.
