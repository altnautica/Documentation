A `LidarDriver` yields point-cloud frames from a spinning, solid-state or single-line ranging device.

## The interface

```python
from ados.sdk.drivers.lidar import (
    LidarDriver,
    LidarCandidate,
    LidarCapabilities,
    LidarSession,
    LidarFrame,
    LidarPoint,
)

class MyLidarDriver(LidarDriver):
    async def discover(self) -> list[LidarCandidate]:
        ...

    async def open(self, candidate, config) -> LidarSession:
        ...

    async def close(self, session) -> None:
        ...

    def capabilities(self, session) -> LidarCapabilities:
        ...

    async def frame_iterator(self, session):
        # async generator yielding LidarFrame
        ...

    async def set_param(self, session, param, value) -> None:
        # rpm, scan rate, filter mode
        ...
```

## Capabilities

```python
LidarCapabilities(
    min_range_m=0.1,
    max_range_m=40.0,
    horizontal_fov_deg=360.0,
    vertical_fov_deg=1.0,
    points_per_frame=1024,
    fps=10.0,
    has_intensity=True,
    has_dual_return=False,
)
```

## Frames

Each `LidarFrame` holds `timestamp_ns`, `sequence`, optional `metadata`, and `points`, a tuple of `LidarPoint` in the sensor body frame: `+x` forward, `+y` left, `+z` up, in metres.

```python
LidarPoint(
    x=2.13, y=-0.42, z=0.05,
    intensity=0.74,
    return_index=0,
)
```

Drivers that get no return at some angles skip those points rather than emit zeros.

## Single-line and spinning sensors

The driver layer does not distinguish single-beam rangefinders from 3D LiDARs. A 1D rangefinder yields frames with `points_per_frame=1`.

## Opening the driver from your plugin

Your plugin calls `discover()`, `open()` and consumes `frame_iterator` itself, then publishes what it derives (nearest obstacle, a downsampled scan) with `ctx.telemetry.extend` or `ctx.events.publish`. The pattern is on [Driver layer](/developers/driver-layer#running-a-driver-from-your-plugin). Most LiDARs need `hardware.uart` or `hardware.usb`.
