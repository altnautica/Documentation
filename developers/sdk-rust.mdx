A plugin's agent half can be written in Python or Rust. This page covers
the Rust SDK, the `ados-sdk` crate. The other option is
[`ados.sdk`](/developers/sdk-python); both speak the same length-prefixed
msgpack wire and capability-token handshake to the plugin host. The wire
lives in `ados-protocol` and is reused unchanged on both sides.

The crate mirrors the Python surface: the IPC client, the plugin
context, the six driver traits, the vision client, a test harness, and
the agent capability catalog re-exported from `ados-protocol`.

## When to pick Rust

Python suits a plugin that leans on the Python ecosystem. Reach for Rust
when:

- **The plugin is a tight, long-running service.** A Rust binary has no
  interpreter to start and a small idle footprint.
- **You ship a vendor binary.** A Rust agent half is one binary at the
  manifest entrypoint. The host execs it directly under systemd with no
  Python environment, and `ctx.process` authorizes any extra vendor
  binary the plugin spawns.
- **You want a single artifact.** The pack step cross-compiles the
  crate and places the binary in the `.adosplug` at the entrypoint path.

## Layout

A Rust agent half is its own crate at `agent/` inside the extension
directory:

```text
extensions/<name>/
  manifest.yaml            # agent.runtime: rust, agent.entrypoint: bin/<name>
  agent/
    Cargo.toml             # the crate
    src/main.rs            # impl Plugin + run_plugin
  locales/ ...             # optional assets, same as any extension
```

The worked examples are
[`extensions/vision-nav`](https://github.com/altnautica/ADOSExtensions/tree/main/extensions/vision-nav)
(one binary) and
[`extensions/world-engine`](https://github.com/altnautica/ADOSExtensions/tree/main/extensions/world-engine)
(several binaries through `bin:<name>` and declared services).

## Depending on the SDK

The crate depends on `ados-sdk`, which brings the IPC client, the
context, the driver traits and the lifecycle runner. It pulls in
`ados-protocol` (the frame, envelope and capability-token wire,
including the vision framebus contract) transitively.

In the
[`altnautica/ADOSExtensions`](https://github.com/altnautica/ADOSExtensions)
monorepo, the Rust agent halves form a cargo workspace. The SDK
dependency is declared once in the root `Cargo.toml` and a member crate
inherits it:

```toml
# extensions/<name>/agent/Cargo.toml
[dependencies]
ados-sdk = { workspace = true }
tokio = { workspace = true }
rmpv = { workspace = true }
# The Plugin trait uses async methods, so implementing it needs the same
# attribute the trait was declared with.
async-trait = { workspace = true }
```

The root workspace resolves `ados-sdk` as a path dependency to a sibling
checkout of the agent repository:

```toml
# Cargo.toml (workspace root)
[workspace.dependencies]
ados-sdk = { path = "../ADOSDroneAgent/crates/ados-sdk" }
ados-protocol = { path = "../ADOSDroneAgent/crates/ados-protocol" }
```

<Note>
An out-of-tree plugin depends on `ados-sdk` from crates.io. Its version
tracks the agent release it speaks to, so pin the agent's major.minor,
for example `ados-sdk = "0.106"`:

```bash
cargo add ados-sdk
```

First-party extensions in ADOSExtensions keep the sibling path
dependency above; CI checks ADOSDroneAgent out at the commit recorded in
the `ADOS_AGENT_REV` file at the workspace root. See
[Rust crates](/developers/rust-crates) for every published ADOS crate.
</Note>

A vision plugin also names `ados-protocol` directly for the framebus
value types the SDK does not re-export (`FrameDescriptor`, `FrameFormat`,
`Detection`, `BoundingBox`, `ModelMetadata`). It is the same crate the
SDK already pulls in.

## The plugin shape

A Rust plugin implements the `Plugin` trait and hands the type to
`run_plugin` from `main`. The trait has one required method, `new`;
every lifecycle hook defaults to a no-op.

```rust
use std::collections::BTreeMap;

use ados_sdk::{run_plugin, Plugin, RunnerError};
use ados_sdk::context::PluginContext;
use ados_sdk::ClientError;
use async_trait::async_trait;

/// A plugin holds whatever state its hooks share.
struct MyPlugin;

#[async_trait]
impl Plugin for MyPlugin {
    fn new() -> Self {
        MyPlugin
    }

    /// Open subscriptions and start work. Each call on `ctx` is gated
    /// on a granted capability.
    async fn on_start(&mut self, ctx: &PluginContext) -> Result<(), ClientError> {
        ctx.events
            .subscribe("vehicle.*", std::sync::Arc::new(|_args| { /* ... */ }))
            .await?;
        Ok(())
    }

    /// Release anything on_start acquired.
    async fn on_stop(&mut self, _ctx: &PluginContext) -> Result<(), ClientError> {
        Ok(())
    }
}

/// Resolve when the process is asked to stop. The host stops the unit
/// with SIGTERM; SIGINT covers a foreground run.
async fn shutdown_signal() {
    use tokio::signal::unix::{signal, SignalKind};
    let mut term = signal(SignalKind::terminate()).expect("SIGTERM handler");
    let mut int = signal(SignalKind::interrupt()).expect("SIGINT handler");
    tokio::select! {
        _ = term.recv() => {}
        _ = int.recv() => {}
    }
}

#[tokio::main]
async fn main() {
    let static_config: BTreeMap<String, rmpv::Value> = BTreeMap::new();
    match run_plugin::<MyPlugin, _>(
        env!("CARGO_PKG_VERSION"),
        static_config,
        shutdown_signal(),
    )
    .await
    {
        Ok(()) => {}
        // Running the binary by hand (no host) lands here: no socket or
        // token to connect to. Report and exit non-zero rather than panic.
        Err(RunnerError::NoBridge) => {
            eprintln!("no plugin host socket/token supplied");
            std::process::exit(1);
        }
        Err(err) => {
            eprintln!("{err}");
            std::process::exit(1);
        }
    }
}
```

The entry is a plain generic function, not a proc-macro, so the call
site stays explicit.

### The runner

`run_plugin` connects the IPC client, builds the `PluginContext` and
drives the hooks. It reads `--socket`, `--token` and `--agent-id` from
the command line, falling back to the values in the
`ados-plugin-token` systemd credential under `$CREDENTIALS_DIRECTORY`,
and to the `ADOS_PLUGIN_*` environment only when there is no credential.
A lost host session ends the run with an error, so the binary exits
non-zero and systemd restarts it with a fresh session. The hook order
matches the Python runner:

```text
on_install -> on_enable -> on_configure(ctx, config) -> on_start
   -> (wait for shutdown) -> on_stop -> on_disable
```

`run_plugin_with` takes pre-parsed `RunnerArgs`, for a test or harness
that supplies arguments without touching the process environment.

## `PluginContext`

The object handed to every hook. Each field is a small capability-gated
facade over one IPC client; the host enforces the capability before the
call reaches a handler.

| Field | What it does | Capability |
| --- | --- | --- |
| `ctx.events` | `publish(topic, payload)` and `subscribe(pattern, cb)` on the event bus | `event.publish` / `event.subscribe` |
| `ctx.mavlink` | `send(...)`, `subscribe(msg_name, cb)`, `register_component(id, kind)` | `mavlink.read` / `mavlink.write` / `mavlink.component.*` |
| `ctx.msp` | Raw MSP to a Betaflight, iNav or KISS flight controller: `send`, `send_raw_rc`, `send_sticks`, `subscribe` | `msp.read` / `msp.write` |
| `ctx.telemetry` | `extend(channel, payload)` to add a channel to the telemetry the GCS reads | `telemetry.extend` |
| `ctx.flight` | `guided_setpoint(args)` and `rate_setpoint(args)` | `flight.guided_setpoint` / `flight.rate_setpoint` |
| `ctx.peripheral_manager` | `register_*_driver(ref)`, `unregister(handle)`, `claim_camera(...)` | `sensor.<kind>.register` |
| `ctx.camera` | `claim(path, exclusive)`, `release(path)`, `get_frame(...)` | The camera hardware capabilities |
| `ctx.vision` | Frame subscription, model registration, inference, detection publishing and subscription, designation, pose injection | `vision.*`, `estimator.pose.inject` |
| `ctx.buttons` | Front-panel button presses; quiet on a board with no panel | `button.subscribe` |
| `ctx.gpio` | `set(chip, pin, high)` and `beep(...)` | `hardware.gpio_out` |
| `ctx.display` | `set_page(...)`: the plugin's page on the onboard display | `display.oled.page` |
| `ctx.radio` | `open_aux_stream`, `send_aux`, `subscribe_aux`, `close_aux_stream` | `radio.aux_stream` |
| `ctx.cloud` | `publish(stream, payload)` and `put_record(...)` | `cloud.publish` / `cloud.records` |
| `ctx.node` | `info()`: the node's profile, board, ground-station role and camera | `node.info.read` |
| `ctx.mdns` | `advertise(...)` and `browse(...)` on the local network | `network.listen` / `network.outbound` |
| `ctx.config` | `static_get(key)` (static config, sync), `get(key, default)` and `set(key, value, scope)` (live) | none |
| `ctx.process` | `spawn(basename, args, env)` to launch an allowlisted vendor binary | `process.spawn` |
| `ctx.lifecycle` | `on_pause(cb)` and `on_resume(cb)` for GCS-side mount events | `event.subscribe` |

`ctx.peripherals` is an alias for `ctx.peripheral_manager`.
`ctx.ping_supervisor()` is a health probe, and `ctx.client()` returns the
shared IPC client for a method no facade covers.

A subscription callback runs on the IPC reader task, so it must not
block. Do cheap work in the callback and move heavy work (an async RPC,
inference) to a spawned task.

## Driver traits

For a hardware-driver plugin, the SDK ships six object-safe async
traits, one per kind, each mirroring the Python base class method for
method: `CameraDriver`, `GimbalDriver`, `LidarDriver`, `GpsDriver`,
`EscDriver` and `PayloadActuatorDriver`. The Python `AsyncIterator`
return becomes a `SampleStream<T>` (a boxed `Stream`), and a `Session`
associated type stands in for the Python session object. The agent does
not route drivers: a driver plugin opens and runs its own device from
its lifecycle hooks. See the [driver layer](/developers/driver-layer).

## Vision

`ctx.vision` is the engine facade. Frames never ride the RPC envelope:
the engine writes normalized frames into a shared-memory ring and
publishes a small descriptor, and the SDK memory-maps the `/dev/shm` ring
read-only and reads each slot through the per-slot seqlock the framebus
contract defines, dropping any torn or stale read (latest wins).

```rust
use std::sync::Arc;
use ados_sdk::vision::Frame;

// In on_start:
let vision = ctx.vision.clone(); // a cheap clone shares the one IPC client
ctx.vision
    .subscribe_frames(None, Arc::new(move |frame: Frame| {
        // frame.descriptor + frame.pixels (resolved from the ring)
        let vision = vision.clone();
        tokio::spawn(async move {
            // run inference, publish a detection ...
        });
    }))
    .await?;
```

The vision client also offers `register_model`, `resolved_model`,
`infer`, `publish_detection` and `publish_one`, `subscribe_detections`,
`designate_track`, `advertise_offload`, and the pose helpers
`register_vio_component`, `inject_pose` and `inject_odometry`. The pose
helpers build a `VISION_POSITION_ESTIMATE` (from a `Pose`) or an
`ODOMETRY` message (from an `Odometry`) and send it under the
visual-odometry component id (`VIO_COMPONENT_ID`), so a plugin never
hand-builds a MAVLink frame.

`Frame`, `Pose`, `Odometry`, `VisionClient` and `VIO_COMPONENT_ID` are
re-exported from the crate root; the framebus value types come from
`ados-protocol`.

The worked vision plugin is
[`vision-nav`](https://github.com/altnautica/ADOSExtensions/tree/main/extensions/vision-nav),
which reads frames from the frame bus, computes optical flow and sends
it to the flight controller.

## Testing

The `ados_sdk::testing` module mirrors the Python harness for vision
plugins. `FakeVisionEngine` emits synthetic frames into the same
`FrameCallback` a plugin registers with `ctx.vision.subscribe_frames`,
and captures the detection batches the plugin publishes, with no host,
vision engine, shared memory or socket.

```rust
use ados_sdk::testing::FakeVisionEngine;
use ados_protocol::framebus::FrameFormat;

let mut engine = FakeVisionEngine::new("uvc-0", 64, 48, FrameFormat::Rgb24);
engine.on_frame(|frame| {
    assert_eq!(frame.descriptor.camera_id, "uvc-0");
});
engine.push_solid(0x80);   // one grey frame
engine.deliver_all();
```

`push_frame`, `push_solid` and `push_dir` enqueue frames (the last reads
`*.bin` and `*.raw` files in name order); `deliver_one` and
`deliver_all` drive them through the resolver; `detection_sink` and
`captured_detections` collect what the plugin published. The module's
own tests in `crates/ados-sdk/src/testing/` are a worked example.

## Capabilities

The SDK re-exports the generated agent capability catalog from
`ados-protocol` as `ados_sdk::capabilities`, so a plugin references one
source of truth for capability ids. The catalog, its risk levels and
which capabilities are enforced are on
[Permissions](/developers/permissions).

A call whose capability was not granted is rejected before it runs; the
SDK surfaces it as `ClientError::CapabilityDenied` naming the missing
capability. A vendor-binary spawn the manifest allowlist refuses
surfaces as `ClientError::AllowlistViolation`.

## IPC

The wire is `ados-protocol` unchanged: length-prefixed msgpack envelope
frames over the per-plugin Unix domain socket, gated by an HMAC
capability token. The handshake presents the token the host minted; the
client then serves requests and responses on one flow (each call gets a
fresh `r<n>` request id) and event, MAVLink and vision pushes on the
other, dispatched to the matching callbacks. The per-request timeout
defaults to five seconds.

## Manifest

A Rust agent half sets `runtime: rust` and points the entrypoint at the
binary path inside the installed plugin tree:

```yaml
agent:
  runtime: rust
  entrypoint: "bin/<name>"
  isolation: subprocess
  permissions:
    - id: vision.frame.read
    - id: vision.detection.publish
  resources:
    max_ram_mb: 32
    max_cpu_percent: 10
    max_pids: 4
```

`scripts/pack-rust.sh` cross-compiles the crate and places the binary at
`agent.entrypoint` in the archive. The host execs that binary directly
under systemd, passing the plugin id and `--socket` on the command line;
the token, agent id and data dir arrive in the `ados-plugin-token`
systemd credential. A plugin that ships binaries for several
architectures uses `bin:<name>` with
[per-architecture binaries](/developers/manifest#per-architecture-binaries).
Signing and install are otherwise identical to a Python plugin; see
[Signing keys](/developers/signing-keys).

A plugin that bundles a vendor binary sets `contains_vendor_binary: true`
and lists each one under `vendor_attribution`; see
[Vendor binaries](/developers/vendor-binaries).
