# MAVLink Signing

MAVLink v2 includes an optional message-signing layer that stamps every outgoing frame with an HMAC-SHA256 tag keyed to a 32-byte shared secret. Once an ArduPilot flight controller holds a key, it rejects unsigned commands on every link except USB. This closes a real attack surface: a peer on the same WiFi, a compromised cloud relay, or a rogue user on the local network cannot inject arm, takeoff, or parameter-write commands even if they reach the MAVLink stream.

In ADOS, the signing key lives in the GCS browser (ADOS Mission Control) as a non-extractable Web Crypto key. The agent never persists the key. It exposes a small REST surface so the GCS can detect capability, push the key to the flight controller once, and clear it again.

<Info>
The key never touches the agent's disk. Raw key bytes exist in the browser only during generation and the one-shot enrollment call. From then on the browser holds a CryptoKey handle that can sign and verify but cannot be exported back to raw bytes, even by the same JavaScript.
</Info>

## How it works

1. The GCS generates 32 random bytes using `crypto.getRandomValues`.
2. The GCS POSTs the key as hex to `/api/mavlink/signing/enroll-fc` over the agent's HMAC-authenticated REST channel.
3. The agent sends a `SETUP_SIGNING` message to the flight controller twice, 200 ms apart, then zeroizes the raw key buffer.
4. The GCS imports the raw bytes as a non-extractable `CryptoKey`, stores the handle in IndexedDB keyed by drone id, and zeroizes its own buffer.
5. Every outgoing MAVLink v2 frame from this drone gets a 13-byte signature tail appended: 1-byte link id, 6-byte timestamp, 6-byte truncated HMAC-SHA256.
6. The agent passes signed frames through the IPC socket to the flight controller unchanged.
7. The flight controller validates each frame and silently drops unsigned or invalid ones, except unsigned frames arriving on its USB port.

## Enabling signing

<Steps>
<Step title="Open the Signing panel">
In the GCS, select your drone, open the Configure tab, and pick the Security section. Choose MAVLink Signing.
</Step>
<Step title="Check capability">
The panel asks the agent which autopilot the flight controller reports in its heartbeat. ArduPilot is supported. If the panel shows "not available", see the [Firmware support](#firmware-support) table below.
</Step>
<Step title="Click Enable signing">
The browser generates a fresh 32-byte key and enrolls it with the flight controller. Enrollment usually completes in under two seconds.
</Step>
<Step title="Verify the fingerprint">
The panel shows an 8-character key id (the first bytes of SHA-256 over the key). Note it if you want to sanity-check that another browser is on the same key later.
</Step>
</Steps>

## What the flight controller enforces

ArduPilot has no parameter that switches enforcement on or off. A non-zero key in its signing store is the switch: from the moment it holds one, it accepts unsigned frames only on its USB port (plus `RADIO_STATUS` from a telemetry radio) and drops them on every other link. Sending an all-zero key clears the store and turns signing off.

The flight controller never acknowledges `SETUP_SIGNING`. The agent reports that it sent the frame, not that the flight controller took it. When a request is interrupted after a frame may have gone out, the GCS keeps both the new key and the previous one and asks the operator which one the flight controller holds. A disable is handled the same way: the GCS keeps the key until the operator confirms unsigned commands are accepted.

<Warning>
Signing can lock you out of your own drone. If every browser that holds the key gets wiped or replaced and you have not exported a copy, the flight controller rejects every command on every link except USB. Recovery: connect over USB and re-enroll, or, from the companion computer, call the `disable-on-fc` endpoint to send a zero-key `SETUP_SIGNING` and then re-enroll from a fresh GCS session.

```bash
curl -X POST http://localhost:8080/api/mavlink/signing/disable-on-fc \
  -H "X-ADOS-Key: your_key"
```
</Warning>

## Rotating keys

Click `Rotate key` in the Signing panel to generate a new 32-byte key and enroll it with the flight controller. The old key is replaced once the agent reports the new one sent; an interrupted rotation keeps both until you confirm which one the flight controller holds. Any other browser still holding the previous key loses its ability to sign until you re-enroll it.

Rotation is a per-browser action today. Each browser that needs to keep working with the rotated key has to re-enroll separately, or import the new key from a browser that already has it.

## Firmware support

| Firmware | Supported | Why |
|---|---|---|
| ArduPilot | Yes | Keeps the key in a persistent on-board store. |
| PX4 | No (for now) | Supports the signing protocol but has no persistent on-board key store. The operator would have to re-provision on every reboot. |
| Betaflight | Not applicable | Uses MSP, not MAVLink. |
| iNav | Not applicable | Uses MSP, not MAVLink. |

Support is decided from the autopilot type in the flight controller's heartbeat. The signing key store is not exposed as parameters, so a parameter dump says nothing about it.

## Agent REST surface

All routes live under `/api/mavlink/signing/` and are gated by the existing `X-ADOS-Key` header.

| Route | Verb | Purpose |
|---|---|---|
| `/capability` | GET | Returns whether the connected FC supports signing, with the firmware name and reason code. |
| `/enroll-fc` | POST | Body: `{ key_hex, link_id }`. Sends `SETUP_SIGNING` to the FC, zeroizes the key buffer, returns the fingerprint. |
| `/disable-on-fc` | POST | Sends `SETUP_SIGNING` with an all-zero key, clearing the FC's signing store. |
| `/counters` | GET | Returns `{ observed, tx_signed_count, rx_signed_count, last_signed_rx_at }`. No observer counts signed frames today, so `observed` is `false` and the counts are `null`. |

Request-body redaction strips `key_hex` from structured logs. The fingerprint (`key_id`) is safe to log and appears in audit entries.

These routes are served natively by the Rust front. Signing is managed from the GCS Configure panel; for SSH-only diagnostics or emergency recovery, call the endpoints above with `curl` on the companion computer (for example, `GET /capability` to check support or `POST /disable-on-fc` to recover from a lockout).

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Panel shows "not available" | The flight controller is not ArduPilot, or it has not sent a heartbeat yet | Check the FC connection on the node Overview, then reopen Signing. |
| Panel shows "Unconfirmed" | An enrollment, rotation, or disable was sent but not confirmed | Send a command from this browser. If it is accepted, settle on the new key (or confirm signing is off); if it is rejected, settle on the previous key (or keep the key). |
| Commands work over USB but not over the radio | The flight controller holds a key this browser does not sign with | Import the key from the browser that enrolled it, or re-enroll from this browser over USB. |
| Fingerprint changed after a reboot | Another browser rotated the key while this one was offline | Import the new key from that browser, or re-enroll from this one. |

## Security posture

What signing protects against:

- Unauthorized command injection over the cloud relay path.
- A WiFi peer on the same access point sending arm or takeoff commands to your drone.
- A compromised agent host (shared cloud relay tenancy, a rogue update) forging commands to the flight controller, because the agent does not hold the key.

What signing does not cover:

- An operator with physical access to the flight controller's UART.
- A browser whose JavaScript execution is compromised by a same-origin XSS payload. The attacker cannot exfiltrate the key thanks to the non-extractable CryptoKey, but they can use it to sign while the session is open.
- Lost-key recovery. Keep a copy of the key fingerprint somewhere you can re-locate.
