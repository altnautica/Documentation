Start with the agent's own checks. They read the same counters Mission Control does and name the broken hop, so you know which section below applies.

## First step: run the agent's checks

```bash
ados                  # status page: services, MAVLink, video, network, next action
ados diag video       # which hop of the video pipeline stopped
ados diag link        # can the radio decode its peer, and how much is lost
ados diag storage     # disk space, write rate and throttle history
```

- `ados diag video` answers "where does video die": it samples each hop twice over 2 s and names the first stalled one.
- `ados diag link` answers "is the radio link working": `healthy`, `searching`, `deaf`, `mis_keyed` or `jammed`, plus measured packet loss.
- `ados diag storage` answers "is the card full or wearing": space first, then write rate and power or thermal throttling.

Add `--json` to any of them, or run `ados status --json`, for a support ticket or a script. See [Drone Agent diagnostics](/drone-agent/diagnostics) for every verdict.

### Read the logs

The Black Box log store is off by default, so the systemd journal is the log of record:

```bash
sudo journalctl -u ados-supervisor -n 100
sudo journalctl -u ados-video --since "10 min ago"
sudo journalctl -u 'ados-*' -p warning --since "1 hour ago"
```

With the [Black Box store](/drone-agent/black-box) turned on, use `ados logs query` and `ados logs tail` instead.

## Flight controller not detected

**Symptoms:** `ados` shows MAVLink not connected. No telemetry in Mission Control.

<AccordionGroup>
  <Accordion title="Check the serial connection">
    Verify the UART cable between the FC and the companion computer. TX goes to RX and RX to TX. Check voltage levels: most FCs use 3.3 V UART; a 5 V TTL port can damage a 3.3 V SBC input.

    List the serial ports:

    ```bash
    ls /dev/tty{S,AMA,ACM,USB}*
    ```

    An FC on USB usually appears as `/dev/ttyACM0` or `/dev/ttyUSB0`.
  </Accordion>

  <Accordion title="Check baud rate">
    The agent sweeps common bauds automatically. To force one, set both `mavlink.serial_port` and `mavlink.baud_rate`. See [What baud your drone is actually running](/drone-agent/mavlink-proxy#what-baud-your-drone-is-actually-running).
  </Accordion>

  <Accordion title="Check for serial port conflicts">
    Another process may hold the port:

    ```bash
    sudo fuser /dev/ttyS0
    ```

    Stop that process, or point the agent at a different port.
  </Accordion>

  <Accordion title="Check the MAVLink protocol setting">
    The agent accepts MAVLink 1 and 2. If the port shows garbled data, confirm the FC's `SERIALn_PROTOCOL` for that port is set to MAVLink.
  </Accordion>

  <Accordion title="FC not sending heartbeats">
    The agent waits for heartbeats to confirm the FC is alive. If none arrive, check that the FC is powered, that MAVLink is enabled on the port you wired, and that the FC is not in a boot loop (watch its LEDs).
  </Accordion>
</AccordionGroup>

## Video frozen or not starting

**Symptoms:** Black video in Mission Control. `ados diag video` reports a `stalled` hop.

<AccordionGroup>
  <Accordion title="Check if a camera is detected">
    ```bash
    ls /dev/video*
    v4l2-ctl --list-devices
    ```

    No `/dev/video*` device means the camera is not recognised. For USB cameras check `lsusb`. For CSI cameras, check that the ribbon cable is seated on both ends.
  </Accordion>

  <Accordion title="Check the video service">
    ```bash
    sudo systemctl status ados-video
    sudo journalctl -u ados-video -n 50
    ```

    Look for errors about the encoder, camera access or mediamtx.
  </Accordion>

  <Accordion title="Check mediamtx">
    ```bash
    curl -s http://localhost:9997/v3/paths/list
    ```

    With the stream up you see a path named `main`. If mediamtx does not answer, check its log lines:

    ```bash
    sudo journalctl -u ados-video --grep "mediamtx" -n 20
    ```
  </Accordion>

  <Accordion title="Check cgroup resource limits">
    The video service has a `MemoryMax` cgroup limit. An OOM kill shows in the journal:

    ```bash
    sudo journalctl -u ados-video --grep "oom|killed|cgroup" -n 20
    ```

    Check the memory events counter:

    ```bash
    cat /sys/fs/cgroup/ados.slice/ados-video.service/memory.events
    ```

    A rising `max` count means the service is hitting its limit.
  </Accordion>

  <Accordion title="Camera permission denied">
    The installer adds the agent user to the `video` group. After a manual install you may need:

    ```bash
    sudo usermod -aG video $(whoami)
    ```

    Then log out and back in.
  </Accordion>
</AccordionGroup>

## Radio link not working

**Symptoms:** No video over WFB-ng. The ground station shows no signal. `ados diag link` reports `deaf`, `mis_keyed` or `jammed`.

<AccordionGroup>
  <Accordion title="Check the WiFi adapter">
    ```bash
    lsusb | grep -i realtek
    ados radio adapters
    ```

    You should see the RTL8812EU with an injection-capable verdict. If not, check the USB connection.
  </Accordion>

  <Accordion title="Check the kernel driver">
    ```bash
    lsmod | grep 8812eu
    sudo dmesg | grep -i 8812eu
    ```

    If the `8812eu` module is missing, rebuild it:

    ```bash
    sudo ados radio install-driver --force
    ```
  </Accordion>

  <Accordion title="Check channel match">
    Open the dashboard [WFB Transmit](/drone-agent/dashboard-transmit) page on the drone and the [WFB Receive](/ground-agent/dashboard-receive) page on the ground station, or run `ados radio status` on both nodes. With auto-hop on, both sides return to the home channel (149 by default) when they lose each other; a different `channel` or `reg_domain` on the two rigs keeps them apart. See [Link automation](/drone-agent/wfb-ng#link-automation).
  </Accordion>

  <Accordion title="Check key match">
    The drone holds `tx.key` and the ground station `rx.key`, complementary halves of one key pair created by a bind. They are not identical files. Compare the fingerprint in `ados radio pair status` on both nodes instead.

    ```bash
    ados radio pair status
    ```

    Different fingerprints, or `mis_keyed` from `ados diag link`, mean the two rigs come from different binds. Re-bind them; see [WFB-ng pairing](/drone-agent/wfb-pairing).
  </Accordion>
</AccordionGroup>

## Cloud disconnected

**Symptoms:** The drone does not appear in Mission Control over the cloud. `ados` shows cloud disconnected.

<AccordionGroup>
  <Accordion title="Check internet connectivity">
    ```bash
    ping -c 3 example.com
    ping -c 3 mqtt.example.com   # your configured MQTT broker host
    ```

    If both fail, the board has no internet. Check WiFi, Ethernet or cellular.
  </Accordion>

  <Accordion title="Check pairing">
    Run `ados`. If the agent is not paired with Mission Control, follow [Pairing](/drone-agent/pairing).
  </Accordion>

  <Accordion title="Check the MQTT connection">
    ```bash
    sudo journalctl -u ados-cloud -n 50
    ```

    Common causes: DNS resolution failure (check `/etc/resolv.conf`), TLS certificate errors from clock skew, or an API key mismatch.
  </Accordion>

  <Accordion title="Check clock synchronization">
    TLS needs an accurate clock. If `date` is off by more than a few minutes, enable NTP:

    ```bash
    sudo timedatectl set-ntp true
    ```
  </Accordion>

  <Accordion title="Check server mode">
    ```bash
    ados status --json
    ```

    The agent is local-only by default. To use the cloud relay or a self-hosted server, open dashboard **Settings** → **Cloud** (see [Agent dashboard: Settings](/drone-agent/dashboard-settings)) and choose the server mode.
  </Accordion>
</AccordionGroup>

## Agent not starting

**Symptoms:** `ados status` reports that the agent is not running.

<AccordionGroup>
  <Accordion title="Check systemd">
    ```bash
    sudo systemctl status ados-supervisor
    sudo journalctl -u ados-supervisor -n 50
    ```
  </Accordion>

  <Accordion title="Reinstall over a broken install">
    Re-run the installer with `--force` to clear its checkpoints and reinstall:

    ```bash
    curl -sSL https://raw.githubusercontent.com/altnautica/ADOSDroneAgent/main/scripts/install.sh | sudo bash -s -- --force
    ```

    See [Install the Drone Agent](/drone-agent/installation) for every installer flag.
  </Accordion>

  <Accordion title="Check disk space">
    ```bash
    df -h /
    ados diag storage
    ```

    A full disk stops the agent. Recordings are stored in per-path subdirectories of `/var/ados/recordings`. Delete segments older than an hour and trim the journal:

    ```bash
    sudo find /var/ados/recordings -name '*.mp4' -mmin +60 -delete
    sudo journalctl --vacuum-size=100M
    ```

    Then run `ados diag storage` again to confirm the footprint dropped.
  </Accordion>
</AccordionGroup>

## High CPU or temperature

<AccordionGroup>
  <Accordion title="Check which process is using resources">
    ```bash
    top -b -n 1 -o %CPU
    ```

    If the video encoder process is near the top, the board may be encoding in software. Check that your board profile lists `h264_enc` under `hw_video_codecs` (see [HAL and tiers](/drone-agent/hal-and-tiers)).
  </Accordion>

  <Accordion title="Thermal throttling">
    ```bash
    cat /sys/class/thermal/thermal_zone0/temp
    ados diag storage
    ```

    Divide the first value by 1000 for degrees Celsius. Above 80 °C the SoC throttles; `ados diag storage` shows whether throttling has occurred in the retained window. Add a heatsink or fan, or reduce video resolution or frame rate.
  </Accordion>
</AccordionGroup>

## High control latency

**Symptoms:** Manual control feels laggy. Mission Control shows a high or climbing `controlRttMs` on the drone card.

<AccordionGroup>
  <Accordion title="Check which path the GCS is using">
    `controlRttMs` is the round-trip time of the control link, measured against the agent's `GET /api/ping`. A few tens of milliseconds is a healthy LAN link. Hundreds of milliseconds points to the MQTT relay or a busy network. Seconds means the GCS is on the cloud command-queue path, which suits monitoring but not hands-on flying.

    For low-latency control, connect over the LAN: serve Mission Control over plain HTTP (`http://localhost:4000` or `http://<lan-ip>:4000`) and pair the agent by IP so the GCS uses the direct WebSocket path.
  </Accordion>

  <Accordion title="Confirm the agent is reachable directly">
    From the GCS machine:

    ```bash
    curl -s -o /dev/null -w "%{time_total}\n" http://192.168.1.50:8080/api/ping
    ```

    Well under a second confirms a healthy direct link. If this is slow or times out while the cloud path works, fix LAN reachability to get the fast path back.
  </Accordion>
</AccordionGroup>

## Getting help

If these steps do not solve the problem:

1. Run `ados support-bundle` on the affected node before rebooting it. It collects status, configuration, diagnostics, log records and service journals into one redacted archive, and sends nothing anywhere.
2. Open an issue on [GitHub](https://github.com/altnautica/ADOSDroneAgent/issues) and attach it.
3. Join the [Discord community](https://discord.gg/uxbvuD4d5q) for real-time help.

See [Support](/operations/support) for what the bundle contains and what makes a report diagnosable.
