Mission Control pairing gives one Mission Control owner an API key for the node, so the node appears in your GCS, telemetry flows, and you can send commands.

ADOS is local-first. The primary path is direct, over the LAN. The cloud path is opt-in, for reaching a node on a different network. An unpaired node still runs local MAVLink, local video and the local REST API.

## Pair over the LAN

<Steps>
  <Step title="Open the pairing dialog">
    In Mission Control, click **Pair New Node** and stay on the **Add a drone** tab.
  </Step>
  <Step title="Enter the node">
    Type the node's hostname, IP address or `.local` name (for example `ados-9f2c1a.local` or `192.168.1.50`), or the 6-character code that `ados status` shows on the node. A code is matched against the nodes advertising on this LAN.
  </Step>
  <Step title="Pair">
    Mission Control probes `/api/pairing/info`, claims the node with `/api/pairing/claim`, and stores the returned API key in the browser. No account or internet connection is needed.
  </Step>
</Steps>

Claiming works only while the node is unpaired, and an unpaired node answers the claim only for callers on its own networks, never for a remote caller arriving through a tunnel. A node in local mode (cloud relay off) is the default and is correct, not a misconfiguration.

If the node answers that it will not pair until its dashboard PIN is set, open its browser dashboard on the same network, set the PIN, and press **Pair** again. See [Agent dashboard: Pairing](/drone-agent/dashboard-pairing).

## Pair across networks

For a node on a different network, sign in to Mission Control. The node must beacon its code to the cloud backend (`pairing.beacon_enabled`). See [Cloud relay](/drone-agent/cloud-relay).

<Steps>
  <Step title="The node holds a pairing code">
    On first boot, or after unpairing, the agent generates a 6-character code (uppercase letters and digits, without `0`, `O`, `1`, `I` or `L`) and keeps it for 24 hours, regenerating it after that or on unpair. `ados status` and the browser dashboard show it.
  </Step>
  <Step title="Enter the code in Mission Control">
    Click **Pair New Node** and type the code on the **Add a drone** tab. When no node on your LAN advertises the code, Mission Control looks it up through the cloud backend. The backend may apply its own, shorter claim window.
  </Step>
  <Step title="The node appears">
    The node shows up in Mission Control with its name, board and live telemetry.
  </Step>
</Steps>

## Pair during install

The **Generate a code** tab in **Pair New Node** creates a code in Mission Control and copies an install command that carries it. Run that command on the node, or pass the code yourself:

```bash
curl -sSL https://raw.githubusercontent.com/altnautica/ADOSDroneAgent/main/scripts/install.sh | sudo bash -s -- --pair YOUR_CODE
```

`--pair <code>` seeds this node's pairing code (and a pending key) so the code you already hold in Mission Control matches the node. Pairing completes when the node checks in. The other installer flags are on [Install the Drone Agent](/drone-agent/installation).

## Pair an existing node

Run `ados` on the node and open the setup URL from the Links panel, or open the browser dashboard at `http://<node>:8080`. If the node is running its hotspot, join it and open `http://192.168.4.1:8080`. The dashboard's pairing page shows the code and the pairing state.

## mDNS discovery

The control front advertises `_ados._tcp` at boot on every profile. While the node is unpaired, the advertisement carries the current pairing code, which is how Mission Control matches a typed code on the LAN and lists the node under **Discovered on your network**.

## Pairing state file

The agent stores pairing state at `/etc/ados/pairing.json`, mode `0600`:

```json
{
  "paired": true,
  "api_key": "ados_...",
  "owner_id": "user_abc123",
  "paired_at": 1713264000
}
```

An unpaired file carries `pairing_code` and `code_created_at` instead. The key is `ados_` followed by 43 base64url characters.

<Warning>
The `api_key` authenticates callers to the node's REST API and the node to the cloud backend. Protect this file and do not share the key.
</Warning>

## API key

Once paired, the REST API requires the `X-ADOS-Key` header on most routes. The CLI reads the key from `/etc/ados/pairing.json` itself. Header format, exempt routes and the dashboard PIN session are on [REST API](/drone-agent/rest-api#authentication).

```bash
curl http://localhost:8080/api/status \
  -H "X-ADOS-Key: ados_..."
```

## Unpairing

Unpair from Mission Control, from the browser dashboard, or on the node:

```bash
ados unpair
```

From the REST API:

```bash
curl -X POST http://localhost:8080/api/pairing/unpair \
  -H "X-ADOS-Key: ados_..."
```

After unpairing:

- The old API key stops working.
- A new pairing code is generated.
- `/etc/ados/pairing.json` is rewritten.
- The node stops sending data through the cloud relay.
- Local MAVLink, video and the REST API keep working.

`ados unpair --radio` also wipes the WFB air-link bind; `--all` releases both.

## Configuration

```yaml
pairing:
  state_path: "/etc/ados/pairing.json"
  beacon_enabled: true
  beacon_interval: 30     # seconds between cloud beacon attempts
  heartbeat_interval: 60  # seconds between heartbeats
```

The full `pairing:` key list is on [Configuration](/drone-agent/configuration).
