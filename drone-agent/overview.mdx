The ADOS Drone Agent is the software that runs on the companion computer inside your drone. It sits between the flight controller (ArduPilot, PX4, Betaflight or iNav) and everything else: your ground station, your phone and the cloud.

It is a hybrid system. The long-running services (the supervisor, MAVLink router, HTTP front, cloud relay, logging store, swarm bus, radio and video pipeline) are native Rust binaries. Python handles vision inference, hardware detection and first-boot bootstrap, and the residual API behind the Rust front. The agent is licensed under GPLv3 and runs on single-board computers from Raspberry Pi to Rockchip to NVIDIA Jetson, plus x86_64 PCs.

## What it does

1. **MAVLink proxy.** Connects to your flight controller over serial and forwards MAVLink to WebSocket and TCP clients, so your ground control station and the cloud share one serial link. See [MAVLink proxy](/drone-agent/mavlink-proxy).
2. **Video pipeline.** Detects your camera (CSI, USB or a network source), encodes H.264 or H.265 in hardware where the board has an encoder, serves it through a local MediaMTX server, and can transmit it over WFB-ng for long-range HD video. See [Video pipeline](/drone-agent/video-pipeline).
3. **Cloud relay.** Opt-in and off by default. It posts a 5 s heartbeat and polls commands over Convex HTTP, relays raw MAVLink over MQTT (WSS 443), and relays WebRTC signaling so a remote browser can reach the drone. On the same LAN, Mission Control connects directly. See [Cloud relay](/drone-agent/cloud-relay).
4. **Service supervisor.** Runs each job as its own systemd unit with automatic restart and memory limits, and starts only the units your node profile needs. See [Systemd services](/drone-agent/systemd-services).

## Architecture at a glance

The agent is a set of processes managed by systemd. `ados-supervisor` is a Rust orchestrator that starts and monitors the other units. The main ones on a drone:

```text
ados-supervisor        # Rust: orchestrator (drives systemd)
  ├── ados-mavlink     # Rust: FC serial <-> MAVLink router (WebSocket :8765)
  ├── ados-swarmbus    # Rust: swarm state bus
  ├── ados-control     # Rust: HTTP front on :8080 (dashboard and REST API)
  ├── ados-api         # Python: residual API behind the front
  ├── ados-cloud       # Rust: MQTT and Convex cloud relay (opt-in)
  ├── ados-logd        # Rust: Black Box logging store (off by default)
  ├── ados-video       # Rust: camera, encoder and MediaMTX
  ├── ados-wfb         # Rust: WFB-ng transmitter
  ├── ados-vision      # Rust: vision engine
  └── ados-plugin-host # Rust: extension host
```

The full unit list per profile is on [Systemd services](/drone-agent/systemd-services).

Services share vehicle data through two Unix domain sockets:

- `/run/ados/mavlink.sock` carries raw binary MAVLink frames (4-byte length prefix plus payload).
- `/run/ados/state.sock` carries the vehicle state as length-prefixed msgpack (`state.v2`, 4-byte big-endian length, body `{v, s}`), about 10 Hz.

## Hardware detection

At install and at boot the agent identifies the board from an optional `/etc/ados/board_override`, the device-tree compatible string and model, then `/proc/cpuinfo`, and loads the matching profile from 21 YAML board profiles. Each profile describes the SoC, buses, video encoders, GPIO and attached hardware. A board with no profile falls back to `generic-arm64` or `generic-x86_64`.

Which services run is decided by the node profile, not by the board. Each board profile also declares a default compute tier, which only matters for extensions that set a minimum tier. See [HAL and tiers](/drone-agent/hal-and-tiers).

## One codebase, four profiles

The same agent installs as one of four profiles:

- **`drone`**: the companion computer on the aircraft. Runs the flight controller link, camera, video transmit and cloud relay.
- **`ground_station`**: a ground-side board that receives WFB-ng video, runs a Wi-Fi hotspot, serves video to a laptop or phone, and can drive an HDMI display and a status screen. See [Ground Agent overview](/ground-agent/overview).
- **`workstation`**: a desktop or laptop node for local compute and the World Engine extension. It has no flight controller link.
- **`compute`**: a headless compute node for offloaded work, also without a flight controller link.

At first boot the agent scores hardware probes (OLED on I2C, an RTL8812 radio, a flight controller on serial, GPS, uplink) and picks `drone` or `ground_station`; ties fall back to the last recorded profile. You can also set the profile at install time with `--profile`. See [Node profiles](/getting-started/node-profiles) for what each profile runs.

## Interfaces

1. **Web dashboard** (port 8080): status, telemetry, video, pairing, extensions, logs, diagnostics and settings; first-run setup steps appear until complete. See [Dashboard](/drone-agent/dashboard-overview).
2. **CLI** (`ados`): a terminal status page, scriptable status, update and uninstall, plus subcommands for hardware, logs, network, plugins, profile, radio and diagnostics. Works over SSH. See [Agent CLI reference](/drone-agent/cli-reference).
3. **REST API** (port 8080): served by the native Rust front, which forwards the remaining routes to the residual Python API. Authenticated routes use `X-ADOS-Key`. See [REST API](/drone-agent/rest-api).
4. **Mission Control**: the ground control station for maps, video, mission planning, hardware management and fleet operations. See [Mission Control overview](/mission-control/overview).
