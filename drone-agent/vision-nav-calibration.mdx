# Calibration

Optical flow does not need a calibration file to fly. Without one, the agent pairs each camera frame with the gyro sample at the same timestamp and assumes the two clocks agree. With one, it applies the measured camera-to-IMU time offset first, so the gyro derotation lines up with the frame it belongs to.

The calibration is a Kalibr-style `camchain.yaml` in the plugin's data directory. The agent reads it once, at start-up.

<Note>
There is no in-app calibration capture in the current release. Produce the file with Kalibr (`kalibr_calibrate_imu_camera`) for the camera and IMU on the vehicle, validate it with the helper below, and copy it onto the drone.
</Note>

## What the agent reads

The file lives at `camchain.yaml` in the plugin's data directory. When the host doesn't hand the plugin a data directory, the agent uses `/var/ados/plugins/com.altnautica.vision-nav/data/camchain.yaml`.

Both Kalibr layouts are accepted:

<CodeGroup>

```yaml Canonical (cam0 wrapper)
cam0:
  camera_model: pinhole
  intrinsics: [1385.4, 1384.1, 1014.2, 760.7]
  distortion_model: radtan
  distortion_coeffs: [-0.3142, 0.1051, 0.00018, -0.00021]
  resolution: [2028, 1520]
  T_cam_imu:
    - [1.00000, 0.00472, -0.00389, 0.00000]
    - [-0.00475, 0.99998, -0.00735, 0.01000]
    - [0.00385, 0.00737, 0.99996, -0.02000]
    - [0.0,     0.0,     0.0,      1.0]
  timeshift_cam_imu: -0.0421
```

```yaml Bare (no cam0 wrapper)
camera_model: pinhole
intrinsics: [1385.4, 1384.1, 1014.2, 760.7]
distortion_model: radtan
distortion_coeffs: [-0.3142, 0.1051, 0.00018, -0.00021]
resolution: [2028, 1520]
T_cam_imu:
  - [1.00000, 0.00472, -0.00389, 0.00000]
  - [-0.00475, 0.99998, -0.00735, 0.01000]
  - [0.00385, 0.00737, 0.99996, -0.02000]
  - [0.0,     0.0,     0.0,      1.0]
timeshift_cam_imu: -0.0421
```

</CodeGroup>

Of all that, the running agent uses one value: `timeshift_cam_imu`, in seconds, Kalibr convention `t_imu = t_cam + timeshift_cam_imu`. A file only counts as a calibration if `intrinsics` has at least four numbers; a missing `timeshift_cam_imu` is read as zero.

When the file loads, the heartbeat reports `cameraIntrinsicsLoaded: true` and the Vision Nav sensors card shows **Calibrated** on the camera row. Otherwise it shows **Not calibrated**, which is fine for optical flow.

## Install a calibration

1. Run Kalibr's camera-IMU calibration for the exact camera, lens, and mount on the vehicle, at the resolution and frame rate you fly.
2. Validate the result with the helper (next section).
3. Copy it to `camchain.yaml` in the plugin's data directory on the drone.
4. Restart the plugin (`ados plugin disable com.altnautica.vision-nav`, then `ados plugin enable com.altnautica.vision-nav`, or toggle it in the Extensions tab). The agent only reads the file at start-up.
5. Check that the camera row on the sensors card reads **Calibrated**.

## Validate before you fly

The `calibration-helper/` package in the extension's source (`altnautica-vision-nav-calib`, Python 3.10+) loads and checks a `camchain.yaml` off the vehicle. It is not part of the runtime and is not shipped in the plugin archive.

```bash
cd extensions/vision-nav/agent/calibration-helper
python -m pip install -e .
python -c "from altnautica_vision_nav_calib import load_intrinsics, load_extrinsics; \
print(load_intrinsics('camchain.yaml')); print(load_extrinsics('camchain.yaml'))"
```

What it rejects:

| Check | Rule |
|---|---|
| Camera model | `pinhole` only |
| Distortion model | `radtan`, `equidistant` (4 coefficients each), or `none` (0) |
| Focal length | `fx > 0` and `fy > 0` |
| Principal point | inside the image (`0 <= cx <= width`, `0 <= cy <= height`) |
| Radial-tangential `k1`, `k2` | magnitude at most 2.0 |
| `T_cam_imu` | bottom row `[0, 0, 0, 1]`, orthonormal rotation, determinant +1 |
| Lever arm | translation at most 1 m (more is almost always a unit error) |
| Timeshift | magnitude at most 0.5 s |

It also warns, without rejecting, when the timeshift is above 0.2 s or when the focal length looks short for a non-fisheye lens. Multi-camera files (`cam1`, `cam2`, ...) are accepted; only `cam0` is read.

## When to recalibrate

- The camera, lens, or mount changed.
- The flight controller (and so the IMU) changed.
- The camera mode changed: resolution, frame rate, or exposure profile. The principal point and the timeshift both move with the mode.
- The sync offset on the sensors card sits in the yellow (10 to 30 ms) or red (above 30 ms) band during a steady hover.

You don't need to recalibrate after every flight. The static offset stays put for a given camera mode; the rolling residual the Vision Nav tab shows is measured against it on every flight.

## The math, briefly

A camera calibration answers three separate questions. Kalibr solves them; this section explains what each one is and why it matters.

### Intrinsics

The camera matrix `K` (`fx, fy, cx, cy`) and the distortion coefficients map pixel coordinates to rays in the camera frame. Calibration fits them to a printed target of known geometry by minimising the per-corner reprojection error across many frames:

```text
min  sum_frames sum_corners || observed_pixel - project(world_corner, K, d, R_f, t_f) ||^2
```

where `d` is the distortion vector and `(R_f, t_f)` is the camera's pose relative to the target in frame `f`. Frames from one angle and distance give nearly degenerate constraints, so many focal-length and principal-point combinations fit equally well. Varied tilt, rotation, and distance across the frames pin down a unique answer. A healthy fit has a mean reprojection error under about 1 pixel; above that, the print scale is usually off or the target flexed.

### Extrinsics

`T_cam_imu` is the fixed rigid transform between the IMU body frame and the camera frame: a 3x3 rotation and a translation (the lever arm, centimetre-scale on a drone). It lets an estimator express gyro and accelerometer readings in the camera's frame.

### Timeshift

The camera and the IMU run on separate clocks, and a USB camera adds its own pipeline delay. `timeshift_cam_imu` is the constant offset between them. Calibration finds it by comparing the camera's rotation rate (from the frame-to-frame target poses) with the gyro trace and searching for the shift that best lines them up:

```text
min_delta  sum_frames || omega_cam(f) - mean(gyro in [t_f + delta, t_(f+1) + delta]) ||^2
```

The motion has to rotate about all three axes. Pure yaw tells the fit nothing about pitch and roll, and the result settles on noise.

### Why optical flow cares about the timeshift

The plugin subtracts the drone's own rotation from the measured flow using the gyro. If the gyro sample is from a few tens of milliseconds before or after the frame, the subtraction is wrong during every turn, and the error shows up as false translation. A good `timeshift_cam_imu` keeps the derotation honest.

### Why an AprilGrid

Kalibr's standard target is an AprilGrid rather than a chessboard:

1. **Occlusion tolerance.** Each tag decodes on its own, so a partly hidden target still yields corners. A chessboard needs every corner visible.
2. **Unique ids.** Each tag carries its id, so every detected corner maps straight to a known 3D point.
3. **Single-tag pose.** Four corners per tag are enough to recover a pose, which helps in steep oblique views.
