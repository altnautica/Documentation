# How Vision Navigation works

This page follows a camera frame from the sensor to the flight controller's state estimate. The first half is the operator's mental model. The second half, from [Module map](#module-map), is the developer reference for the compiled agent half.

## The pieces

**Inputs:**

- **Camera frames** from the agent's shared vision frame bus. The vision host owns the camera (USB UVC or CSI); the plugin subscribes to the stream and never opens a device.
- **Gyro** from the flight controller's MAVLink `RAW_IMU`, the path every flight controller publishes. Used to remove rotation from the measured flow.
- **Rangefinder** (in `optical_flow`): the flight controller's `DISTANCE_SENSOR`, or a TF-Luna on a companion UART.
- **Altitude messages** (in `optical_flow_degraded`): `GLOBAL_POSITION_INT`, `VFR_HUD`, and `GPS_RAW_INT` for the scale ladder.
- **`TIMESYNC`** replies from the flight controller, to align the two clocks.

**Output** on MAVLink component 198:

- `OPTICAL_FLOW_RAD` (#106) at the camera frame rate, around 30 Hz.
- `DISTANCE_SENSOR` (#132) alongside each flow sample when the rangefinder is wired to the companion.
- `TIMESYNC` (#111) and a 1 Hz `HEARTBEAT` carrying the companion state.

## The chain

```text
camera -> vision host -> frame bus -> plugin -> OPTICAL_FLOW_RAD -> FC EKF
                                        ^                              |
                                        |                              v
                         gyro + rangefinder / altitude        position and velocity
```

On every frame the plugin:

1. **Converts** the frame (`nv12`, `yuv420p`, or `rgb24`) to grayscale. The frame-bus callback never blocks; it hands the frame to a worker task.
2. **Pairs** it with the gyro sample taken at the same instant. The time aligner interpolates between the two IMU samples around the frame time, after applying the `timeshift_cam_imu` offset from the calibration file (zero when there is none).
3. **Estimates** flow with the active mode's estimator. The Lucas-Kanade tracker picks up to 200 Shi-Tomasi corners spread on a grid, tracks each through a 3-level pyramid, drops outliers, and takes the median of the displacements.
4. **Emits** `OPTICAL_FLOW_RAD` on component 198, with `time_usec` converted to the flight controller's clock.
5. **Updates health**: flow quality, flow rate, distance, scale source, sync offset, estimator state, and the pre-arm report. A 1 Hz tick publishes that snapshot as the `navigation` heartbeat block.

## How the flight controller fuses it

The plugin does not change flight controller parameters. You set them once:

- **ArduPilot**: `FLOW_TYPE = 5` accepts `OPTICAL_FLOW_RAD` from MAVLink, and an EKF3 source set with `EK3_SRCn_VELXY = 5` uses it for horizontal velocity.
- **PX4**: `EKF2_OF_CTRL` enables flow fusion.
- **iNav 7.0+**: `opflow_hardware = MAVLINK` and `nav_use_optflow_for_poshold = ON`.

The EKF fuses each sample subject to its own gating (innovation checks, delay, the quality field). The `quality` field is the plugin's main lever: in `optical_flow_degraded` it is scaled down per scale source so the EKF trusts weaker heights less. See [Configure optical flow](/drone-agent/vision-nav-optical-flow).

## What the plugin does that the flight controller can't

1. **Talk to the camera.** The flight controller can't read a USB or CSI camera. The agent captures it and the plugin tracks it.
2. **Run the vision.** The EKF is good at fusing a velocity measurement; it doesn't run a feature tracker.
3. **Report honestly.** The plugin watches its own inputs, labels the estimator state, and publishes a pre-arm report so you don't arm on a bad feed.

## What Mission Control shows

The **Vision Nav** tab on the drone detail panel reads the `navigation` heartbeat block:

- **Companion pill** in the header: active, critical, terminating, or offline.
- **Fallback banner**: appears when the estimator is `degraded` or `failed`, with the most likely cause and a next step.
- **Mode card**: the modes the agent advertises, with the active one marked and the estimator state pill. Read-only.
- **Sensors card**: camera device and whether a calibration file was loaded; IMU source, rate, and sync offset; rangefinder topology, distance, and scale source.
- **Estimator card**: engine (Lucas-Kanade, or Lucas-Kanade (degraded)), state, flow quality, and sync offset.
- **Telemetry trends**: 60 seconds of flow quality and sync offset.
- **Flow health** and **Pre-arm** cards.
- **Firmware parameters**: the reference list for ArduPilot, PX4, or iNav, or an explanation on Betaflight.

A short guided tour runs the first time; **Replay tour** in the header runs it again.

## Fallback and recovery

The plugin assumes every input degrades at some point and makes that visible. Four mechanisms do the work.

### 1. The scale ladder

`optical_flow_degraded` has no rangefinder, so it walks a four-rung height ladder every frame: the flight controller's baro-fused relative altitude (quality x0.7), raw `VFR_HUD` altitude minus take-off (x0.6), GPS height outdoors (x0.4), and a fixed 1.5 m (x0.2). See [Modes](/drone-agent/vision-nav-modes) for the triggers.

**Why not stop emitting on the last rung?** An EKF with nothing else to fuse is better off with a heavily de-weighted velocity hint than with none. The fixed rung is the lowest-quality emission the plugin makes, and the estimator reports `degraded` the whole time it is on it.

```text
GLOBAL_POSITION_INT.relative_alt  --fresh-->  quality x0.7
        | stale (> 2 s)
VFR_HUD.alt - take-off             --fresh-->  quality x0.6
        | stale
GPS_RAW_INT.alt - take-off         --outdoor, 3D fix, eph <= 200 cm-->  quality x0.4
        | not healthy
fixed 1.5 m                        ---------->  quality x0.2, state degraded
```

Height is clamped to 0.3 to 50 m on every rung.

### 2. Camera-IMU sync bands

The time aligner tracks the residual between each frame and its paired gyro sample over a rolling 60-sample window and reports the average as `cameraImuSyncOffsetMs`. The Vision Nav tab colours it:

| Band | Average residual |
|---|---|
| Green | 10 ms or less |
| Yellow | 10 to 30 ms |
| Red | above 30 ms |

The sync offset is shown, not gated: no pre-arm check reads it. When the estimator is degraded and the offset is above 30 ms, the fallback banner names sync drift as the cause and suggests re-checking the calibration. Tens of milliseconds are typical on a USB UVC camera with software timestamps.

### 3. The companion state machine

The companion's state follows the estimator. A `converged` sample makes it active. A `degraded` or `failed` streak of 2 seconds flips it to critical. The state rides the 1 Hz `HEARTBEAT` on component 198 as `MAV_STATE_STANDBY`, `MAV_STATE_ACTIVE`, or `MAV_STATE_CRITICAL`, and drives the `companion_active` pre-arm check and the pill on the Vision Nav tab.

### 4. The flight controller's own source switch

The plugin never switches EKF source sets and never changes flight mode. That stays with you and the flight controller: on ArduPilot, configure a GPS source set and an optical-flow source set and switch between them with the flight controller's RC source-set option; on PX4, a source change is a parameter write and an EKF restart. Switching back to GPS at altitude is the standard recovery when vision degrades.

### How they combine

A flight that goes wrong might look like this:

1. Light fades over a smooth floor. Flow quality drops below 50 and the estimator reports `degraded`.
2. The fallback banner appears: quality below the safe gate, slow the yaw and fly over more texture.
3. Two seconds later the companion goes critical; the pill turns red.
4. You flip the flight controller to its GPS source set (or land). The plugin keeps emitting low-quality samples, which the EKF now ignores, so you can switch back when conditions improve.

### What the plugin does not detect

The plugin has no frame-loss timer of its own. If the camera stops delivering frames, the plugin simply stops emitting, and the flight controller's EKF times out the flow source by its own rules. On the Vision Nav tab the tell is a flow-rate trend that stops updating.

## Module map

The agent half is a compiled Rust binary (`bin/vision-nav`). The plugin host execs it under systemd, passes the per-plugin socket on the command line and the capability token and agent id through the unit environment, and the binary runs until `SIGTERM`. The crate lives at `extensions/vision-nav/agent/` in ADOSExtensions:

```text
extensions/vision-nav/
  manifest.yaml          # id, permissions, resources, component 198, Engage Skill
  config-schema.json     # the per-drone configuration
  agent/
    Cargo.toml
    src/
      main.rs            # entry point: builds the plugin, runs to SIGTERM
      lib.rs             # module declarations
      config.rs          # per-drone config parse + validation (mirrors config-schema.json)
      framing.rs         # luma extraction from nv12 / yuv420p / rgb24 frames
      flow.rs            # sparse pyramidal Lucas-Kanade tracker
      estimator.rs       # Estimator trait, EstimatorOutput, EstimatorState
      estimators.rs      # off / optical_flow / optical_flow_degraded + the registry
      scale.rs           # the rangefinder-free height ladder
      rangefinder.rs     # FC relay, TF-Luna UART, I2C stubs
      imu.rs             # RAW_IMU ring buffer + frame/IMU time aligner
      clock_align.rs     # bidirectional TIMESYNC clock alignment
      mavlink_emit.rs    # message builders + the component router
      pre_arm.rs         # the mode-aware pre-arm gate
      health.rs          # companion state + the navigation heartbeat block
      pipeline.rs        # plugin lifecycle, subscriptions, the per-frame worker
    calibration-helper/  # Python camchain.yaml validators (not shipped in the archive)
  gcs/                   # the Mission Control half (Vision Nav tab, Engage Skill)
  locales/               # translation strings
```

### The estimator contract

Every estimator answers `step(...)` with an `EstimatorOutput`, or `None` when there's not enough input this frame (warm-up, no trackable features):

```rust
pub struct EstimatorOutput {
    pub timestamp_us: i64,
    pub output_mode: OutputMode,            // OpticalFlow | None
    pub state: EstimatorState,              // off|init|converging|converged|degraded|failed
    pub flow_rate_x: Option<f32>,
    pub flow_rate_y: Option<f32>,
    pub flow_rate_z: Option<f32>,
    pub flow_quality: Option<i32>,          // 0-255
    pub flow_distance_m: Option<f32>,
    pub flow_scale_source: Option<ScaleSourceLabel>, // rangefinder|baro|gps|vision
    pub integration_time_us: Option<i64>,
}
```

The component router reads `output_mode`: an `OpticalFlow` sample becomes `OPTICAL_FLOW_RAD` on component 198, a `None` sample (from `off`) sends nothing.

### Sequence: one frame in `optical_flow`

```text
1. The vision host publishes a frame on the shared frame bus. The plugin's
   subscription callback converts it with framing::frame_to_gray and sends
   it down a channel.
2. The worker pairs (prev_gray, curr_gray, dt) and asks imu::TimeAligner
   for the gyro sample at the frame time.
3. The rangefinder trait returns the latest reading (FC relay readings
   older than 200 ms count as missing).
4. estimators::OpticalFlowEstimator::step runs flow::OpticalFlowLk and
   returns an EstimatorOutput.
5. mavlink_emit::ComponentRouter::emit sends OPTICAL_FLOW_RAD on component
   198; a companion rangefinder also sends DISTANCE_SENSOR.
6. The companion state machine and pre_arm::PreArmGate update, and
   health::HealthSnapshot is refreshed.
7. The 1 Hz health tick publishes the navigation block and the
   navigation.engage state event.
```

### Clock alignment

Once a second the plugin sends `TIMESYNC(tc1 = 0, ts1 = now)`. The flight controller replies with its own time in `tc1`, and the plugin folds `tc1 - ts1` into an exponential moving average (alpha 0.1). That offset converts the plugin's monotonic clock into flight controller time for every `time_usec` it sends.

### Rangefinder drivers

`rangefinder.rs` implements four sources behind one trait:

| Driver | Topology | Status |
|---|---|---|
| `fc_relay` | `fc` | Implemented. Relays the flight controller's `DISTANCE_SENSOR`. The default when no rangefinder is configured. |
| `tfluna_uart` | `companion` | Implemented. Pure 9-byte Benewake frame parser; default device `/dev/ttyUSB0` at 115200 baud. |
| `garmin_lidarlite_i2c` | `companion` | Stub that returns no reading until the plugin SDK exposes an I2C facade. Wire the sensor to the flight controller and use `fc_relay`. |
| `vl53l1x_i2c` | `companion` | Same as above. |

### The pre-arm gate

`pre_arm::PreArmGate::evaluate()` is a pure function: no MAVLink, no filesystem, no async. It returns a report with a list of checks, each with a severity (`ok`, `pending`, `blocking`) and a detail string; `armable` is true only when every check is `ok` (or the list is empty, in `off`). The flow-quality gate follows the config's `flow_quality_min` (default 50).

### The heartbeat block

Every second the plugin pushes the `navigation` block through `ctx.telemetry.extend("navigation", ...)`. Keys are camelCase end to end; a snake_case key is dropped by the cloud relay's validator.

```json
{
  "opticalFlowSupported": true,
  "rangefinderTopology": "fc",
  "recommendedCameraId": "/dev/video0",
  "flowQuality": 180,
  "flowRateHz": 29.5,
  "flowDistanceM": 1.25,
  "companionState": "active",
  "mode": "optical_flow",
  "availableEstimators": ["off", "optical_flow", "optical_flow_degraded"],
  "estimatorState": "converged",
  "flowScaleSource": "rangefinder",
  "imuSource": "mavlink-raw-imu",
  "imuRateHz": 100,
  "cameraImuSyncOffsetMs": 4.2,
  "cameraIntrinsicsLoaded": false,
  "preArmReport": {
    "mode": "optical_flow",
    "armable": true,
    "checks": [
      {"id": "companion_active", "severity": "ok", "detail": ""},
      {"id": "flow_quality", "severity": "ok", "detail": "Quality 180/255."},
      {"id": "rangefinder", "severity": "ok", "detail": "Topology: fc"}
    ]
  },
  "suggestedMode": null,
  "suggestedModeReason": null,
  "detectedCameraCount": null,

```

The four `suggested*` / `detected*` keys are part of the block's shape but the current agent leaves them `null`. The block rides the cloud relay's `cmd_droneStatus.navigation` field into Mission Control's per-drone store.

### Adding a mode

1. Implement the `Estimator` trait in `estimators.rs` (or a new module): `estimator_id`, `output_mode`, `step`.
2. Add its id to `available_estimators()` so the heartbeat advertises it and the mode card lists it.
3. Add the variant to `Mode` in `config.rs` and to the `mode` enum in `config-schema.json`.
4. Add a branch to `PreArmGate::evaluate()` with the checks it needs.
5. Add the mode to `ModeCard.tsx` and `EstimatorCard.tsx` in the GCS half.
6. Write unit tests for its state machine and output shape.

The pipeline does not change.
