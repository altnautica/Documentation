ADOS is built local-first. The design assumption is that the network a node sits on is a network you control. This page is about what that assumption buys, where it breaks, and what to do about it.

## Radio range is authority

<Warning>
Anything within radio range of a paired fleet has substantial authority over it.

A request relayed over the radio from the linked ground station reaches the drone with that ground station's full authority over the node's operating surface: telemetry, parameters, configuration, services, plugins, and flight control. Only a short denylist of routes that change who the node trusts (pairing, credential issuance, radio pairing, flight-controller signing removal, factory and setup reset, cloud posture, remote access) is refused over the relay. The [armed interlock](/operations/safety#what-the-agent-refuses-while-armed) still applies to relayed requests.

Plan around it. Treat a paired node the way you would treat a machine with an open shell, and factory reset anything that leaves your control.
</Warning>

### The per-pair relay secret

A fleet shares one radio keypair, so the radio key alone cannot tell one ground station from another. Each relayed request therefore carries a relay ticket: an HMAC bound to that exact method, path, and body, single use, and keyed from a secret the ground station generates for each drone it pairs. A second ground station holding the same fleet radio key cannot mint a ticket the drone accepts, because it does not hold that drone's secret.

The ground station delivers the secret to the drone at pair time through `POST /api/relay/peer-secret`, over the radio. The drone stores it owner-only under `/etc/ados/secrets/` and the first write wins: a drone that already holds a secret refuses a different one, and the only way to replace it is to unpair the drone, which clears it.

That delivery is trust on first use. An attacker already listening on the radio at the moment of pairing can observe the secret. The exposure is one exchange at pair time rather than every request afterwards, so pair in a place and at a time you control.

## The credentials a node holds

| Credential | Location | What it grants |
|---|---|---|
| Pairing key | `/etc/ados/pairing.json`, mode 0600 | The entire agent API. It is not scoped. |
| Radio keypair | `/etc/ados/wfb/`, `/etc/drone.key`, `/etc/gs.key`, mode 0600 | Fleet membership, and with it the radio link to the other nodes |
| Dashboard PIN | `/etc/ados/dashboard-pin.json`, mode 0600 | Browser dashboard sessions |
| AP passphrase | `/etc/ados/ap-passphrase`, mode 0600 | The ground station's WiFi network |
| MCP token | `/etc/ados/mcp-token.json` | An alternative to the pairing key at the auth edge |
| Service secrets | `/etc/ados/secrets/` | Tunnel token, setup token, relay peer secret |

The pairing key is the one to be careful with. It is presented as an `X-ADOS-Key` header and it grants the whole data plane with no scoping: telemetry, parameters, configuration writes, service control, plugin installation. There is no read-only variant.

## Default credentials

**No default password ships for SSH or for the dashboard.**

- **SSH is not managed by ADOS at all.** The agent does not configure sshd, does not set a password, and does not touch root login or password authentication. Whatever your OS image shipped with is what you have. If that image has a default account and password, change it. This is the most likely default credential on your box, and it is not one ADOS can fix for you.
- The installer creates a system account with no login shell and no home directory, and sets no password on it.
- **The dashboard has no default PIN.** On an unpaired node with no PIN file present, the first visitor from the LAN sets one. Once the node is paired, setting the first PIN needs the pairing key or a caller on the box itself. Set it yourself, from the box, before the box goes anywhere.
- **The AP passphrase is generated per unit** on first boot rather than shipped as a shared string. See [WiFi AP mode](/ground-agent/wifi-ap#the-ap-passphrase).

<Note>
Two caveats on the AP passphrase. A value set in `network.hotspot.password` takes precedence over the generated one, so an image carrying that key gives every unit built from it the same passphrase. And if the system cannot produce randomness the generator fails closed: nothing is written and the access point does not come up, rather than substituting a string every unit would share. Check the passphrase the box is actually using rather than assuming it generated one.
</Note>

## Locking down the access point

The ground station's access point is WPA2-PSK with a per-unit passphrase, so it is not open. What to do beyond that:

1. **Read the generated passphrase and keep it.** The installer summary, the `ados` status page, and the on-box panel all show it. The panel also shows a join QR code. `ados network ap-passphrase` prints the value on its own with nothing around it, which is the one to use from a script or a pipe.
2. **Do not put a shared passphrase in a fleet image.** If `network.hotspot.password` is set, every unit from that image shares one credential.
3. **Turn the AP off if you do not use it.** Only if you have another way in. Disabling the AP on a box with no Ethernet and no USB tether means a monitor and keyboard to get it back.
4. **Treat AP clients as trusted.** Devices on the AP reach the agent API, the video stream, and the MAVLink WebSocket. The AP subnet is treated as an operator route even on an unpaired box, which is what makes a fresh unit claimable.

## Set the dashboard PIN

The browser dashboard is gated by a 4 to 12 digit PIN. A correct PIN mints a session token presented as `X-ADOS-Dashboard-Session`.

Set it from the box before deployment. Leaving it unset means the first visitor from the LAN sets it, which is convenient at the bench and wrong in the field.

Wrong attempts lock out on a ladder: 5 wrong attempts locks for 30 seconds, 10 for 5 minutes, 15 for 30 minutes. A 4 digit PIN is a convenience gate whose real defences are the file mode, the reach boundary, and that lockout, not the strength of the PIN. Do not treat it as protection against an attacker already on your network.

Clearing or changing the PIN rotates its salt, which revokes every live session. Full dashboard access rules are on [Agent dashboard overview](/drone-agent/dashboard-overview#access-and-authentication).

## The network ports

| Port | Carries | Authentication |
|---|---|---|
| 8080 | Agent REST API and dashboard | Pairing key, or a dashboard session |
| 8765 | MAVLink WebSocket | Ticket or pairing key. `mavlink.ws_proxy_enforce_auth` defaults on, so a paired node refuses a handshake that carries neither. |
| 5760 | Raw MAVLink over TCP | No credential channel. Unpaired: open to any caller. Paired: the box itself only, unless `mavlink.raw_proxy_lan_access` is set. |
| 14550, 14551 | Raw MAVLink over UDP | Same posture and flags as 5760. |

The raw MAVLink endpoints speak to the flight controller, and a MAVLink byte stream has no handshake and no headers, so there is nowhere for a caller to carry a credential and the peer address is the only thing the agent learns. Their posture follows the pairing state. An unpaired node admits any caller, so a desktop GCS can attach to a fresh unit. A paired node serves them to the box itself only, and refuses every off-box peer, the access point and USB gadget networks included.

`mavlink.raw_proxy_lan_access` (default `false`) reopens a paired node's raw ports to off-box peers, which is what a desktop ground station on your LAN needs. `mavlink.raw_proxy_enforce_auth` (default `false`) is the lockdown in the other direction: on an unpaired node it narrows the raw ports to the box and its first-boot lifelines (loopback, link-local, the access point, and the USB gadget link), and on a paired node it keeps off-box peers refused even with LAN access on. The posture in force is reported as `mavlink_proxy_posture` in the agent's status telemetry. The WebSocket on 8765 enforces by default because it has two channels a caller can use, the `X-ADOS-Key` header and the `ados-ws-ticket` subprotocol; while unpaired it admits only the box and its first-boot lifelines.

<Warning>
Do not expose 8080, 8765, 5760, 14550, or 14551 to the internet, and do not put a powered-up drone on a network you do not control. Anything that can reach 5760 can command the flight controller.
</Warning>

The API is open when the node is unpaired, but only from a narrow set of peers: loopback, link-local, a device on the node's own access point, and a host on the USB gadget link. Another host on your LAN gets data only behind a dashboard PIN session. The public pairing routes answer the LAN so a fresh box can be claimed, but the claim itself, which hands out the node's key, is refused to a remote caller: a public-internet host, or any request that arrives through a proxy or tunnel. Pair a node promptly rather than leaving it unpaired on a shared network.

Loopback traffic is treated as on-box and bypasses API authentication, on the reasoning that a local shell already exceeds anything the API could grant. A forwarding header disqualifies a request from that treatment, so a tunnel terminating on localhost cannot impersonate a local operator.

## Factory reset

A factory reset returns a node to its first-boot posture: every standing credential, the node's identity, its configuration, and its logs are deleted. It does not wipe the filesystem and does not remove the agent. There are two ways to run one.

**The script**, `scripts/factory-reset.sh` in the ADOSDroneAgent repository, works on any profile. Run it as root on the node; it stops the supervisor, asks for confirmation (pass `--force` to skip the prompt), and deletes the files below.

```bash
sudo bash factory-reset.sh
sudo reboot
```

**The API path**, `POST /api/v1/ground-station/factory-reset?confirm=<token>`, exists only on a ground station (any other profile answers `404`). It is refused with `403 E_NOT_ON_BOX` unless the caller is on the box itself, so a remote operator holding the pairing key cannot wipe a node, and it is refused over the radio relay. The `confirm` token is the installed fleet key's fingerprint (`ados radio pair status` prints it), or `factory-reset-unpaired` on a station that holds no fleet key; a mismatch answers `400 E_CONFIRM_MISMATCH`. While the vehicle state reads armed, the armed interlock refuses it. Before wiping, it moves the station to the `direct` mesh role and unpairs the radio; if the role change fails, nothing is wiped.

### What a factory reset clears

| Item | Path | Script | API path |
|---|---|---|---|
| Pairing key | `/etc/ados/pairing.json` | cleared | cleared |
| Dashboard PIN | `/etc/ados/dashboard-pin.json` | cleared | cleared |
| MCP token | `/etc/ados/mcp-token.json` | cleared | cleared |
| AP passphrase | `/etc/ados/ap-passphrase` | cleared | cleared |
| Service secrets, including the relay peer secret | `/etc/ados/secrets/` | cleared | cleared |
| Radio keys | `/etc/ados/wfb/`, `/etc/drone.key`, `/etc/gs.key` | cleared | cleared |
| TLS certificates | `/etc/ados/certs/` | cleared | cleared |
| Setup-complete marker | `/var/lib/ados/setup-complete` | cleared | cleared |
| Device ID | `/etc/ados/device-id` | cleared | cleared |
| Configuration | `/etc/ados/config.yaml` | cleared | cleared |
| Logs | `/var/log/ados/` | cleared | cleared |
| Mesh identity, revocations, role, and gateway pin | `/etc/ados/mesh/` | kept | cleared |
| Profile | `/etc/ados/profile.conf` | **kept** | **kept** |
| Hostname | system hostname | **kept** | **kept** |

`profile.conf` is kept on purpose: it records what the hardware is, not who owns it, and without it a later upgrade can re-profile the box into the wrong kind of node. The hostname is kept too, so a node handed to someone else still carries the name you gave it.

After a reset, reboot. The box comes up in setup mode with auto-pair on and a freshly generated AP passphrase, so read the new one off the on-box panel or with `ados network ap-passphrase`.

## Before a node leaves your control

1. Run `ados support-bundle` if you want a record of its state.
2. Factory reset it.
3. Confirm the pairing key, radio keys, and AP passphrase are gone.
4. Re-pair the remaining fleet if that node held fleet radio keys. Its copy of the fleet key is what gave it the radio link to the others.
5. Reflash if the node held anything you care about beyond what the reset deletes, such as recordings or flight logs outside `/var/log/ados/`.
